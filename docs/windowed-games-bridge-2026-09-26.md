# Windowed Doom/Wolf: concrete source-port bridge

Research record, 2026-09-26. No game port, accelerated driver or 30 fps result is claimed by this document. The next implementation is a cooperative source-port API, not a promise that an arbitrary existing DOS executable is virtualized.

## Smallest executable route

Use a 32-bit DOS/DPMI game with a linear 320×200 indexed framebuffer. After each rendered frame, copy64000 bytes and the palette into a parent-owned conventional-memory transfer allocation. Invoke a real-mode FAR service through DPMI INT31/AX0301, supplying a dedicated real-mode stack. That service calls the retained shell presenter synchronously, then returns to native protected-mode game execution. The presenter converts the game's palette to the selected desktop pixel format and scales/clips only its window's client area.

This avoids executing the existing real-mode/unreal-LFB presenter from protected mode. The service must check CR0.PE=0: DPMI's real-mode interface may execute in V86 under another monitor, so the protocol alone does not guarantee the current renderer is usable. The existing HDPMI implementation is at `build/external/HX/Src/HDPMI/I31SWT.ASM:_callrmproc`, supporting0300/0301/0302; use0301's ordinary RETF contract rather than hand-written raw mode transitions. Its register structure carries explicit CS:IP and SS:SP. A first bridge probe must establish state restoration and actual presentation under the packaged HDPMI/extender before integrating a game. [DPMI0301 specification](https://www.delorie.com/djgpp/doc/dpmi/api/310301.html), [HDPMI source](https://github.com/Baron-von-Riedesel/HX/blob/43182b4a0efd008ae5aab3ccfcc6d644437cd111/Src/HDPMI/I31SWT.ASM).

The service boundary should provide discovery/version, indexed-surface descriptor, palette sequence, completed-frame sequence, present/poll, focused make/break key events, mouse deltas and normal-close request. A transfer block can hold64000 pixels +768 RGB palette bytes +128 key events and header within64KiB; the real-mode stack must be in a separate allocation. Do not address a64000-byte buffer with a nonzero base offset that crosses the segment boundary. Keep the allocation parent-owned through EXEC and release only after the child has returned and callbacks stopped.

Drive presentation from the game's foreground frame and polling calls. The BIOS18.2Hz timer alone cannot produce30 distinct frames per second. `DG_SleepMs`/equivalent waiting loops must also call the host poll service to keep desktop input responsive. The host must never call DOS/EXEC from this callback. Ordinary Files/application launches stay deferred until the child exits. One supported game can run; this does not establish independent background processes.

Raw keyboard make/break events are necessary: BIOS INT16 queue entries cannot represent every key release. Add a host-owned event queue and a focus-generation reset so keys cannot remain held after losing focus. Keep existing BIOS translation/keyboard ownership intact. Audio integration must coordinate the existing HDPMI/VSBHDA owner; do not initialize a second competing monitor or reprogram its timer/PIC blindly.

## Acceleration that the devices really expose

GPU rectangle copies can accelerate retained-window movement, fills and offscreen presentation. They do not turn these software ray/column renderers into hardware3D engines. Palette conversion and2× pixel expansion also remain CPU work unless a separately implemented compatible scaling/format-conversion engine is used.

## Performance gate

At320×200, one indexed frame is64KB. A640×400×32-bit visible window is1,024,000 bytes:30 presentations/s require at least30.72MB/s of final-pixel writes, before scaling/composition/overlap costs. This is arithmetic, not measured speed. Avoid full-desktop repaints and measure engine rendering, bridge transition, conversion, transfer and host processing separately.

The first end-to-end acceptance must show the actual source-port game running inside the retained GUI, responsive make/break controls, palette effects, movement/occlusion of its window, normal quit and subsequent fullscreen applications. Record completed unique frames and wall time plus frame-time distribution, QEMU accelerator/CPU/display settings and the actual image hashes. Emulated host timing is not a PentiumIII/T23/E500 benchmark. A30fps target becomes a supported claim only after the required physical machines/configurations achieve it.
