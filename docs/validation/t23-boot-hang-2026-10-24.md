# T23 boot hang, source 56e58374

Investigation and host evidence: `build/codex/hang-report.md`. No hardware,
QEMU or image-build validation is claimed by this change.

## Sources checked before implementation

- [POSIX poll](https://pubs.opengroup.org/onlinepubs/9799919799/functions/poll.html)
  and [Linux poll(2)](https://man7.org/linux/man-pages/man2/poll.2.html):
  readiness describes an operation that will not block. Observing readiness
  does not consume device state. Test the desktop's actual state-read path
  rather than converting its device events to edge-triggered notifications.
- [Intel/Microsoft APM BIOS 1.2, February 1996](https://intel-vintage-developer.eu5.org/IAL/POWERMGM/APMV12.PDF),
  sections 4.6.2, 4.6.5, 4.6.15 and 4.6.17: real-mode connect is 5301h;
  disconnect is 5304h; Get Capabilities is 5310h after connection/version
  negotiation. Error 03h means interface not connected. A refusal at the
  monitor's entry is a transport failure, not a BIOS refusal.
- [Upstream Linux APM implementation](https://github.com/torvalds/linux/blob/v6.12/arch/x86/kernel/apm_32.c)
  corroborates the separation of BIOS error returns and transport failure.
- [Upstream mutex design](https://docs.kernel.org/locking/mutex-design.html)
  describes queueing/sleeping after uncontended acquisition fails, rather
  than repeatedly abandoning and recreating a queued mutex acquisition.

The existing backend intentionally grants power operations 2000 ms. The
broker must scope that admitted bound to an APM call, subtract queue time,
and restore the ordinary monitor bound afterwards. It must not widen generic
input or DOS firmware access. G10's DPMS and G11b's 5310h allowlist do not
change the existing 5301h request or its missing monitor budget.

## Publication mutex decision

The native cache mutex reserves FIFO tickets for sleeping tasks. Two FAT
publishers can each leave `cache_reservation_wait`, enter their VFS guard,
and fail `cache_publish`'s optimistic mutex acquisition because the other
publisher already has the next ticket. Their retries hand the mutex back
and forth without publishing. Pthread mutex replays do not preserve that
queued-ticket state. The production FIFO replay fails at `result==0` on the
original cache implementation (`build/codex/publish-before.log`). A second
replay uses real coroutine stacks: the original cache alternates 1001 marker
attempts and 1000 storage-writer attempts, with zero accepted publications
and zero device commands; the corrected cache publishes once per task.

Publication now queues for the cache bookkeeping mutex in the established
namespace → volume → cache order, as `cache_peek` already does. This narrows
the earlier “without waiting” rule: publication still does not wait for
credits, slots, barriers, transport or pins under its VFS guard. Those
conditions retain EAGAIN and release the guard before waiting. Contention
for the bookkeeping mutex itself must use FIFO admission rather than an
unbounded optimistic retry. Cache transport and condition waits release the
mutex; its refresh callback copies retained device fields without entering
VFS. No cache → namespace acquisition is introduced.

## Host validation

The native FIFO negative control fails on the original cache source after
2001 publication attempts and zero accepted publications; the corrected
source accepts both publications in six task switches. The real FAT32 test
mounts E: at +1615 ms beside marker/log activity, retains deferred ownership
scanning and trusted FSInfo, and performs no free-space observation I/O.
An explicit cache-refusal injection verifies the 2-second
`publication_retry` record, including task name/id, operation and phase.
The desktop worker/watch replay consumes both media and mixer readiness.

Cache reservation/writeback, FAT transaction/concurrency, desktop/mixer,
APM backend/provider/T23 and production V86 broker tests pass. The broker's
2000 ms APM calls fail before the budget correction and pass after it.
Every touched C file passes an i686 check; the four kernel files use the
exact flags from `scripts/build_kernel.py`. All runs use `nice -n 19`.
No QEMU, systemd scope or boot image build was run. The old serial log
cannot supply the blocked instruction; physical T23 confirmation remains
outstanding. Detailed results and before/after logs are in `build/codex/`.
