## Research and implementation decisions

The approved boot-memory/f0-acceptance contracts were checked against:

- [QEMU fw_cfg specification](https://www.qemu.org/docs/master/specs/fw_cfg.html)
  and [QEMU 9.2 command-line implementation](https://raw.githubusercontent.com/qemu/qemu/v9.2.0/system/vl.c):
  x86 selector/data ports 510h/511h, signature, big-endian directory
  fields, and exact string bytes without a terminating NUL. The loader
  gates all such accesses on checked SMBIOS type-1 manufacturer QEMU,
  uses PIO only and enforces finite directory/request limits.
- [ACPI 6.5 system address-map interface](https://uefi.org/specs/ACPI/6.5/15_System_Address_Map_Interfaces.html):
  E820 20/24-byte records, continuation, attributes and types. The
  implementation uses a 64-bit boundary sweep; only inward-rounded
  type-1 ranges can contain kernel extents. Invalid/truncated maps stop.
- [Microsoft FAT specification](https://academy.cba.mit.edu/classes/networking_communications/SD/FAT.pdf):
  FAT type by cluster count, BPB, short directory entries, FAT32 links,
  FSInfo and backup structures. BIOS access is read-only; no INT21 or
  legacy unpartitioned FAT16 assumptions are reused.
- [VBE Core 3.0](https://pdos.csail.mit.edu/6.828/2012/readings/hardware/vbe3.pdf)
  and [SeaBIOS 1.16.3 VBE implementation](https://raw.githubusercontent.com/coreboot/seabios/rel-1.16.3/vgasrc/vbe.c):
  VBE3 linear pitch/masks, LFB mode set/read-back and mode-information
  refresh. Candidates are checked for pitch, memory size, framebuffer
  overflow and nonoverlapping masks before selection.
- [ELF specification](https://refspecs.linuxfoundation.org/elf/elf.pdf):
  ELF32 executable/program headers and virtual entry. All PT_LOAD
  physical extents are checked before copies. The stub has a virtual
  entry 0xC0100000 in a PT_LOAD at physical 0x00100000 and a second
  segment with BSS.
- [SMBIOS 3.8 specification](https://www.dmtf.org/sites/default/files/standards/documents/DSP0134_3.8.0.pdf)
  and [SeaBIOS table placement](https://raw.githubusercontent.com/coreboot/seabios/rel-1.16.3/src/fw/biostables.c):
  checked 2.x/3.x entry points and bounded string walking. Table reads
  before A20 are limited to below 1 MiB. Large SeaBIOS tables may be
  placed higher; this implementation records that entry address but
  leaves QEMU detection unavailable in that case.
- [SeaBIOS bounded PS/2 waits](https://raw.githubusercontent.com/coreboot/seabios/rel-1.16.3/src/hw/ps2port.c):
  boundedness principle only. The repository's ATI/ESS/subsystem
  firmware-first rule is included unchanged; no claim about native
  E500 controller qualification is made.

Implementation-specific choices, for lead review: the contracts do not
give binary offsets for the loader header, BOOT.CFG token syntax, or a
tie-break order between non-RAM E820 types. The chosen 16-byte CLDR
header, simple option tokens and conservative non-RAM precedence are
documented in src/boot/README.md. No frozen-handoff defect was found.

## Checks actually run

T0 PASS:

- NASM binary assembly of MBR and complete loader.
- NASM ELF32 plus ld.lld linking of the diagnostic stub.
- Six Python unittest checks: every C/NASM v1 field offset and total
  size; MBR size/signature/table/signature-slot separation; loader
  header/CRC and one-byte corruption; bad header/size/entry rejection;
  stub virtual-to-physical entry and BSS; raw evidence-parser fixtures
  and missing/reordered/failing marker rejection.
- All six checks also passed under Python -O after T1 assertions were
  converted to unconditional validation. Both modes were rerun after
  the last source changes. Python and the documented shell command
  syntax, plus new-file whitespace checks, also passed.

The stub linker result has two PT_LOADs with separate R/E and R/W
permissions, physical start 0x00100000, and virtual entry 0xC0100000.
The assembled loader is 23,040 bytes (45 sectors). MBR is 512 bytes,
with code/data confined to bytes 0–439, disk signature/reserved bytes
440–445, partition table 446–509 and signature 510–511.

## Handoff and remaining qualification

The lead must run the capped image build and the documented matrix,
retain actual serial logs and image SHA-256, and integrate the loader
checks with the canonical runner. Assembly success does not validate BIOS
register preservation, unreal-mode behavior or the hardware paths.
CHS, KBC A20 fallback, physical menu/UART, synthetic invalid E820 and
negative ELF cases remain untested at runtime. SMBIOS tables above
1 MiB, more than 512 video modes, more than 256 fw_cfg files, more than
32 ELF headers and more than 128 normalized ranges are bounded limits.

The diagnostic stub is not the production kernel and does not implement
the eleven kernel acceptance probes. It does not establish timer progress,
allocator/protection/scheduler correctness or physical-laptop support.
Main build-path replacement, diary entry, suspended-release policy,
Windows-bundle requalification and final cross-review remain lead work.
