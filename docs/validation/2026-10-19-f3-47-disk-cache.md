# F3-47: private DOS disk cache (host validation)

Research checked before implementation, 2026-10-19:

- [Microsoft MS-DOS 6.22 SMARTDRV help (preserved original)](https://www.infania.net/misc/dos622help/smartdrv.html): extended-memory read cache, `/B` read-ahead, `/X` disables write-behind. Keep the VFS and overlay writes synchronous; cache reads at the VM image boundary, with exact overlay coherence. The global block-cache policy and FAT code stay unchanged.
- [id Software DOOM `z_zone.c`](https://github.com/id-Software/DOOM/blob/master/linuxdoom-1.10/z_zone.c) and [`w_wad.c`](https://github.com/id-Software/DOOM/blob/master/linuxdoom-1.10/w_wad.c): `Z_Init` obtains the zone through `I_ZoneBase`; purgeable lump owners are cleared on eviction and `W_CacheLumpNum` reloads missing lumps.
- [id Software released platform code](https://github.com/id-Software/DOOM/blob/master/linuxdoom-1.10/i_system.c): Linux defaults to 6 MiB. This is not evidence for DOS command-line behavior.
- [DOS revision reconstruction, `i_ibm.c`](https://github.com/gamesrc-ver-recreation/doom/blob/master/i_ibm.c): `I_ZoneBase` caps the DOS zone at 8 MiB and has no `-maxzone` parser. This is a reconstruction, not id's released DOS platform source. `I_BeginRead`/`I_EndRead` draw the game's own floppy icon at (304,184). The desktop tray in this checkout contains network, volume, removable-media presence and notifications, with no INT 13h activity connection. These directive discrepancies require the lead's decision; no guest graphics rewriting is justified by the cache work.

Implementation and measured results are recorded in `build/codex/f3-47-report.md`.

## Implementation and host measurements

The private cache is an LRU of 64 KiB blocks, charged to `MM_VM_PRIVATE`
inside the existing commitment: 512 KiB for an 8 MiB VM, 2 MiB for the
32 MiB default. Base fills merge indexed overlay sectors before publishing
validity; successful writes update resident data, and failed writes invalidate
it. Read-ahead failure falls back to the requested authoritative sector.
Close, image replacement and failed creation release all cache pages.

A deterministic production-service trace uses seed 47, a synthesized 12 MiB
image and 384 stable 1–64 KiB lump ranges (which may overlap). Each run has
2,000 warm-up and 2,000 measured logical requests at 400 requests/s. The VFS
transport generates data; there is no ATA latency or real DOS/game execution.

| Measured 5 s window | Two 64 KiB windows | 2 MiB LRU |
| --- | ---: | ---: |
| Uniform random: host reads | 2,992 | 2,381 |
| Uniform random: host bytes | 196,083,712 | 156,041,216 |
| Uniform random: wholly cached requests / 2,000 | 21 | 324 |
| Uniform random: sector hit rate | 97.76% | 98.21% |
| Uniform random: distinct 64 KiB regions | 181 | 181 |
| Uniform random: histogram | 2032,0,0,0,0 | 2032,0,0,0,0 |
| Uniform random: maximum whole-hit request | 8.98 µs | 18.14 µs |

Histogram bins are `<100`, `[100,1000)`, `[1000,10000)`, `[10000,50000]`,
`>50000` µs. The extra BIOS calls are 64 KiB requests split at the BIOS's
127-sector limit. Host reads fall 20.42%; a 2 MiB cache does not achieve
95% whole-request hits over the larger random working set. Sector hits
exceed 95%, and a warmed 32-region trace has 2,000/2,000 wholly cached
requests with zero host reads (maximum whole-hit request 21.09 µs).

A FIFO capacity model, with 3 MiB reserved for static game data, reduces
issued lump reads from 1,526 at a 6 MiB zone to 3 at 16 MiB; with the LRU,
host reads fall from 1,929 to 3. This models purgeable capacity, not the exact
DOOM zone allocator or a verified effect of a DOS command-line option.

The default host fixture reserves 32 MiB, with 29,241,848 resident bytes,
a 24 MiB guest pool and 512 cache pages (2 MiB). Largest/total pool free
are 25,165,824/25,165,824 bytes at boot; real 0500h service returns
25,149,440/25,149,440 after synthetic DPMI entry and
24,100,864/24,100,864 after a representative 1 MiB program allocation.
A further 16 MiB 0501h allocation succeeds. Actual DOS/4GW startup memory
still requires hardware capture; the new `vm_perf_mem` rows retain the
first/latest 0500h and latest post-0501h snapshots for that purpose.

The launcher/manifest and desktop tray are unchanged pending clarification
of the source discrepancies above. The requested 100 ms activity hold time
is not implemented; there is no existing tray disk-activity signal to alter.
No public ABI change, image build, QEMU run or hardware validation is claimed.

## Amendment 1

The lead withdrew the tray indicator/100 ms hold-time requirement: the
floppy icon is drawn by DOS DOOM itself, around WAD reads. The lead also
dropped `-maxzone`; the bundled DOS binary caps the zone at 8 MiB and has
no such option. The launcher remains unchanged. The source links above
were rechecked before the amendment; the DOS source remains reconstruction
evidence, not an official DOS platform release.

The cache now rounds image size up to 64 KiB, with a 16 MiB ceiling, and
falls back to 2 MiB if the larger allocation exceeds commitment headroom.
It reserves the worker charge during creation and handles failure even
when the fallback cannot fit. Regression coverage includes rounding, both
headroom boundaries, 32-block and 256-block eviction, and ownership/unwind
at the first, middle and last block of a full 16 MiB allocation.

The unchanged 32 MiB commitment/24 MiB eager pool cannot accommodate a
12 MiB cache. Host traces therefore distinguish a controlled zero-pool,
32 MiB commitment envelope from the actual default VM. The former obtains
a 12 MiB cache; the latter correctly falls back to 2 MiB. No pool quota,
admission cap or physical-memory limit is changed. Host verification of
0500h/0501h and the interval memory records is retained.

Final trace measurements, the 16 MiB ledger arithmetic for a 256 MiB T23,
and rerun results are appended to `build/codex/f3-47-report.md` under
"Amendment 1". They do not establish actual T23 memory availability or
DOS/4GW execution; the lead must collect the `maximum-vm-created` ledger
profile and decide the default game's cache budget before claiming the
full-image cache behavior for that VM.

Amendment reruns passed: the full host suite exited 0 (53,664,419 DOS VM
checks, 4,098 log-recovery checks, 2,102,351 power-cut checks). The enlarged
12 MiB fixture had 1,526/1,526 wholly cached zone6 requests and zero host
reads after warm-up; both hot32 envelopes had 2,000/2,000 hits. The actual
default zone6 fallback still had 169/1,526 wholly cached requests and 1,929
host reads. All tests ran sequentially with `nice -n 19`; the optional DOS
guest runner skipped for the absent DOSBOOT image. The subsequent kernel
build and FPU/SIMD audit passed: ELF 5,995,156 bytes, SHA-256
`625a60e04102b5fdfcc2bd5859df762636276bb9311e03a70aa8cb8bd458e832`.
`git diff --check` passed. No OS image, QEMU or hardware run is included.

## Amendment 2

The lead's 48 MiB default commitment replaces the earlier budget limitation.
`DOSVM_HEADROOM` remains an independent 32 MiB; the eager guest pool remains
24 MiB. The 8 MiB bound on low memory/devices/tables excludes disk cache
backing, which is still charged to `MM_VM_PRIVATE` and the total commitment.
The production default creation path now supplies the full-image trace;
an explicit pool-plus-low commitment exercises the constrained fallback.

Research rechecked before this amendment:
[Microsoft's original SMARTDRV INT13 documentation](https://github.com/microsoft/MS-DOS/blob/main/v4.0/src/DEV/SMARTDRV/INT13.DOC)
describes extended-memory cache backing and explicit cache-size selection.
The local `dosvm_create`/`read_cache_open` comparison showed that the eager
pool plus a full-image cache exceeded the former commitment and that the
final non-pool bound also included cache pages. Decision: apply the lead's
budget, keep admission arithmetic and pool allocation unchanged, and charge
the image cache separately within that budget. This remains a CiukiOS VMM
decision, not a claim about NTVDM or a Windows memory-manager implementation.

The host suite replays page-owner charges measured from default
`dosvm_create` with a 16 MiB cache through the production PMM and f0-43
ledger. It captures boot-end, settled-desktop, maximum-vm-created and
teardown profiles on 128/256/512 MiB E820 models. Declared model inputs are:
the entire first 16 MiB unavailable to general allocation (1 MiB low area
and a 15 MiB kernel-image allowance, including static VM metadata); 4 MiB
heap, 1.5 MiB tables, 8 MiB global cache; then 3 MiB shared desktop backing.
These are budget assumptions derived from the boot-memory targets, not
measured desktop or T23 allocations. VM backing uses actual host-harness
owner counts; worker stack and rounded task/FPU backing are added explicitly
because that transport fake uses malloc. VM metadata is already in the
kernel allowance and is not allocated or counted a second time.

All model stages reconcile physical owner counts, preserve separate
commitment/residency and cache/pool categories, and require admission plus
32 MiB headroom and remaining VM promises to fit. No paging, overcommit,
global cache-policy change or automatic commitment retry is introduced.
Probe-suite budget predicates and synthetic records resolve constants from
the public DOS VM header rather than carrying another numeric default.
Unknown named constants fail closed. Final measured tables and rerun
results are appended under "Amendment 2" in `build/codex/f3-47-report.md`.

The 128 MiB `vm-memory` probe already accepts a second-VM admission refusal;
its suite now requires that outcome (`ENOMEM`, no second boot). Two default
promises plus headroom need 128 MiB before host deductions, which cannot
fit that model. The T23/E500 second-VM success expectations remain. The host
window/isolation harness uses a 256 MiB transport for simultaneous default
VMs; a separate test withholds RAM to exercise the exact first-admission
boundary and a second refusal without allocating any backing.

Final Amendment 2 verification passed: full host kernel suite (exit 0,
53,868,395 DOS VM checks, 4,098 recovery checks and 2,102,351 power-cut
checks), then 23 affected Python tests, sequentially with `nice -n 19`.
Default zone6: 1,526/1,526 wholly cached requests, zero host reads/bytes,
maximum whole-hit request 49.549 µs. Hot32 retains 100% hits and zero reads,

56,983,552 / 191,201,280 / 459,636,736 free bytes at 128/256/512 MiB; all
preserve independent headroom and outstanding promises with no pressure.
These are modeled budgets, not measured hardware profiles.
