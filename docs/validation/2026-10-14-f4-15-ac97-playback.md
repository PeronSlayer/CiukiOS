# F4-15 AC'97 late refill and exhausted-ring recovery

Research checked before implementation, 2026-10-14. QEMU and T23 audible
qualification belong to the lead; this worktree supplies host evidence.

## Sources and decision

- Intel [82801CAM ICH3-M datasheet, 290716-001](https://edbatalha.info/compaq-n610c/Intel%2082801%20ICH3-M%2029071601.pdf),
  §§13.2.1–13.2.7: BDL/CIV/LVI/PIV use a 32-entry ring. PIV identifies a
  prefetched descriptor; the specification does not require PIV=CIV+1.
  DCH alone also describes a software pause. CELV distinguishes exhausted
  LVI; LVBCI/BCIS are latched W1C events, so IRQ acknowledgement may already
  have cleared them. PICB describes fetch progress, not analog playback.
  RR requires RUN clear. Preserve the existing 512-word stereo period;
  the PICB table's DWords wording conflicts with the established transport
  units and the implementations below.
- Linux [intel8x0.c v6.12](https://raw.githubusercontent.com/torvalds/linux/v6.12/sound/pci/intel8x0.c),
  `snd_intel8x0_update`, `snd_intel8x0_pcm_pointer`, setup/trigger: modulo-32
  retirement/LVI advancement, Intel word counts, and coherent CIV/PICB
  retries. PIV equality is not used to validate playback progress.
- QEMU [AC97 v9.2.0](https://raw.githubusercontent.com/qemu/qemu/v9.2.0/hw/audio/ac97.c),
  `transfer_audio`, `nabm_writeb`: exhaustion leaves CIV=LVI, PICB=0 and
  DCH/CELV; BUP=0 supplies zero samples. Preserve this model and the runtime
  profiles. Retain separate host handoffs where PIV has not advanced.

The supplied garbled `293c05af` capture retains `remaining=0 piv=8 sr=000f`,
then `play=failed civ=8` and `retired=209 running=1 active=0`. The complete
published count and LVI are unavailable. `(8 - (209 % 32)) & 31 = 23`:

- At an eight-period window (`published=217`) the existing
  `delta >= outstanding` comparison fails. This is not a legal forward
  wrap; accept neither this movement nor fabricated fetched frames.
- With `published=233`, LVI=8 and a late native idle tail, 23 periods of
  forward movement fit. The previous PIV=CIV+1 comparison rejects PIV=8
  before retirement. With PIV=9 the next failure is the unconditional DCH
  error. These host replays explain failure paths, not a proven reconstruction
  of the garbled physical capture.
- A worker reaching the last running descriptor cannot publish into its
  prefetched successor. The old publication path failed the backend; mixing
  had already consumed the source quantum before that refusal.

Implement bounded catch-up to the existing lead, without widening active
latency. Retry a protected publication without consuming another quantum.
Recover only a coherent DCH/CELV with RUN still set, zero PICB,
CIV=LVI=(published-1)%32 and non-regressing fetch position. Account fetched data first, prove RUN clear
and a stable halted cursor, reset the channel, rebase the output timeline,
and prime a complete eight-period silence lead before restarting, including
when the source became inactive with nonzero PCM still queued. A refused
unpublished quantum is preserved once at the new generation's start, with
the remaining lead filled with silence. Normal startup remains paced at one
period per service; a partially primed transport completes even if the
initiating source becomes inactive. Do not replay old PCM. Invalid indices,
LVI mismatch, impossible progress, unexpected halt and persistent cursor
regression remain failures. Record CIV/LVI/PIV/PICB/SR and absolute counters
before rollback in one backend failure line. A failed pause/reset retains
the triggering snapshot even if the hardware has already reset CIV/LVI.
Keep the record within the ordinary logger's 254-character payload budget
(maximum 227 characters, including the operation and service-gap/elapsed
diagnostics). The shorter separate `play=failed` record is no longer emitted.

The existing descriptors clear BUP (bit 30), so an exhausted output engine
supplies silence rather than replaying the last PCM sample. The host engine
now obeys LVI exhaustion instead of advancing CIV indefinitely; it covers
the QEMU CIV+1 PIV sequence as well as independent PIV=CIV observations.
Runtime QEMU profiles, its codec model and the period/count units are unchanged.

This recovery makes DMA fetch counters monotonic across channel resets; it
does not prove that all fetched samples reached the speakers before a reset.
The existing silent idle-tail stop remains in place. Audible recovery and
continuous sound for the full physical session still require the T23 retest.

The existing serial timer sends a bounded FIFO burst with no UART wait.
`serial_write` can synchronously drain a queued log when entered with IF
clear. This is a possible source of lateness, not proof of the T23 trigger;
serial changes remain f4-14's scope. Recovery itself emits no log while
restarting DMA.

## F4-23 controller reset compatibility

Research checked before implementation, 2026-10-14:

- Intel [82801AA/AB datasheet, 290655-003](https://www.cpu-galaxy.at/CPU/Ram%20Rom%20Eprom/Other_Intel_chips/other_intel-Dateien/82801AA_Datasheet.pdf),
  §§5.18.2–5.18.4, 12.2.8–12.2.9, and the
  [ICH3-M datasheet above](https://edbatalha.info/compaq-n610c/Intel%2082801%20ICH3-M%2029071601.pdf),
  §§5.18.3–5.18.5, 13.2.8–13.2.9: Cold Reset# is active low;
  software releases it by setting bit 1. The existing 1 ms assertion exceeds
  the specified 1 µs pulse. Warm reset resumes a suspended link without
  resetting codec registers. Keep the cold sequence and the bounded
  one-second primary-ready wait for physical controllers.
- [QEMU AC97 v9.2.0](https://raw.githubusercontent.com/qemu/qemu/v9.2.0/hw/audio/ac97.c),
  `nabm_writel` lines 818–824 ignores writes setting GC_CR or GC_WR;
  `nabm_readl` lines 718–724 always reports GS_S0CR. `nam_readw`
  lines 480–484 reads the mixer without testing either reset or readiness;
  `mixer_reset` initializes it on device reset and NAM register 00h writes.
  Byte/DWord NAM reads return all ones; in-range word reads do not.

The failure is the release-write readback: writing GLOB_CNT=2 leaves zero
in QEMU. No codec transaction has occurred at that point. `ext2a=ffff`
and `rate2c=ffff` are initialized diagnostic sentinels, not mixer readbacks;
`valid=00` confirms that distinction. Neither a longer wait nor warm reset
fixes the ignored write.

Retain the physical reset writes/readbacks. Permit the exact zero release
readback only for the existing SMBIOS-QEMU plus Intel 8086:2415 twin guard;
apply the same narrow exception in the codec link check. Log `reset=cold`
or `reset=qemu_model` with observed control/status after primary readiness.
The codec reset, CAS, identity, response, rate, attenuation and silent DMA
proofs remain mandatory. ICH3-M (8086:2485), even with the QEMU boot flag,
cannot take the exception.

Host coverage uses QEMU's actual ignored-write/always-ready/word-mixer
behavior separately from a stricter physical model that returns FFFF until
Cold Reset# is released and primary readiness arrives. That latter behavior
is a defensive hardware model, not a claim about upstream QEMU. Results
are recorded in `build/codex/f4-23-report.md`; runtime QEMU and T23 audible
qualification remain with the lead.
