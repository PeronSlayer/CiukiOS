# Browser JavaScript worker design

## Decision

Run JavaScript in a separate preemptible 32-bit DPMI worker, never in the
16-bit browser CAPP or in a CVSESSION ring-0 device handler. The browser keeps
network ownership, HTML parsing, layout, and painting. The worker receives
bounded script jobs through a versioned shared-memory mailbox and returns
bounded DOM operations; it does not receive UI pointers or call DOS, BIOS, or
kernel services.

The existing CAPP is a small-model 16-bit program with a 64 KiB image ceiling;
the current browser is already close to that limit. The repository has a
DJGPP cross-compiler and launches DOS/4GW programs through DPMIRUN/VMFORK.
Those facts make a 32-bit user-mode worker a more plausible home for an engine
than adding one to the browser image. The current CN32 retained-process path
is not a drop-in alternative: its native step is capped at 256 instructions
and scheduling currently advances at the VMM tick cadence.

Use MicroQuickJS (mQuickJS) as the first engine candidate. Upstream describes
an ES5-near subset, a caller-supplied memory arena, no engine `malloc`/`free`,
and a C interrupt callback. Its published footprint is about 100 KiB of
ARM Thumb-2 code including the C library and about 10 KiB RAM; these are
upstream figures, not measurements of the DJGPP build. The MIT license is
compatible with inclusion. Elk is smaller, but its upstream documents
substantial JavaScript omissions and a dual AGPL/commercial license, so it is a
poorer fit for ordinary web scripts.

## Message and execution boundaries

The worker uses one synchronous RPC mailbox, not transport rings. The packed
64-byte CWW header carries the operation, request/completion sequence, flags,
lengths, error and heartbeat. The worker maps a locked shared XMS region; input
and output windows are each 24,576 bytes at fixed offsets. Root-side dispatch
copies requests and results, and the worker runs as a separate preemptible
DPMI process. TLS network steps and JavaScript jobs share this RPC mechanism;
no pointer crosses the mailbox. Cancellation/navigation generations are not
currently represented by a separate job queue.

The adapter accepts a source span of at most 64 KiB, copies exactly that span
to a worker-owned buffer, and writes a NUL at the copied buffer's end before
calling `JS_Eval`. This is required by upstream mQuickJS: its `JS_Eval` and
`JS_Parse` implementation explicitly assumes `input[input_len]` is NUL. A
mailbox or file buffer's following byte is outside the source span and cannot
be used as its terminator. The host regression fixture places a throwing
statement immediately after the span and verifies that it is not executed.

The generated atom table requires 512-byte alignment, while the DJGPP COFF
section alignment is lower. The worker therefore copies the table into an
aligned buffer and relocates only offsets from the explicit `JS_ROM_VALUE` slot
list generated by CiukiOS' mQuickJS builder. It separately copies the C
function table and rebases its known ROM-name entries, leaving immediate
one-character names intact. A tag-only scan of every 32-bit table word is
incorrect: on the DOS image the table occupied `0x59f0..0x7f5c`, and ASCII
`Id\0\0` (`0x6449`) inside the `getElementById` atom looked like a tagged
pointer. This corrupted the DOM method binding. The regression now uses that
low-address range synthetically, checks a listed pointer is relocated, and
checks the unlisted ASCII word is preserved.

The JavaScript adapter exposes a constrained DOM surface: `document.write`,
`document.getElementById`, and the returned element's `id`, `textContent`, and
`innerHTML`; `alert` and console/print output are bounded or ignored. The worker
seeds up to 32 ID/text snapshots (at most 1,024 text bytes each), evaluates
scripts, and returns bounded TLV mutations. The page adapter applies those
mutations to a local page file and hands the resulting HTML back to the
browser. It does not pass UI pointers to JavaScript. This is a deliberately
small DOM bridge, not a standards-complete HTML parser. Script warnings retain
the failing script ordinal and bounded JavaScript exception message.

Current limits are a 1 MiB HTML input/output page, at most 16 executable
scripts, 64 KiB per inline or external script, 256 KiB aggregate script source,
and a 24 KiB TLV response. Only classic JavaScript MIME types are executed;
module, JSON, and other script types are skipped. The parser recognizes
comments, skips raw-text/RCDATA regions such as `style`, `textarea`, and
`title`, and handles nested same-name elements and simple quoted/unquoted
attributes. It does not implement the HTML5 tree-construction algorithm,
entity decoding, full CSS, event attributes, timers, asynchronous jobs,
`document.createElement`, or a general-purpose DOM.

mQuickJS polls its interrupt callback for a per-script budget. The adapter
allows 256 callback intervals, so execution is aborted rather than resumed
when the budget is exhausted. A separate 30-second process-clock budget is
checked between scripts. The process is preemptible, keeping script
execution out of ring 0 and outside the 16-bit browser process.

## Scope and validation

This provides a constrained JavaScript subset, not a complete browser DOM or
modern ECMAScript implementation, and it does not provide Internet Explorer
or other browser-equivalence compatibility. CSS support remains separate. TLS
and JavaScript execute in the user-mode worker; network ownership and the
browser's URL fetching/layout remain outside the engine.

The upstream engine and worker compile for the DJGPP target. The JS adapter's
host regression harness passed with ASan/UBSan on both 32-bit and 64-bit hosts,
including the non-NUL source span and synthetic DOS-address ROM-relocation
cases. The page-adapter host harness passed with comment, raw-text spoofing,
non-JavaScript MIME, nested-element, and page-buffer-growth fixtures. The final
worker binary has been rebuilt. VM validation of actual script effects is
underway; desktop responsiveness, target memory footprint, and page behavior
remain subject to runtime validation.

## Primary sources

- [MicroQuickJS upstream README](https://github.com/bellard/mquickjs): subset,
  stated footprint, supplied arena, no engine allocator, and MIT license.
- [MicroQuickJS C API](https://github.com/bellard/mquickjs/blob/main/mquickjs.h):
  `JS_SetInterruptHandler`, `JS_Parse`, and `JS_Run` interfaces.
- [MicroQuickJS implementation](https://raw.githubusercontent.com/bellard/mquickjs/main/mquickjs.c):
  interrupt polling counter and context callback storage. `JS_Parse` and
  `JS_Eval` require `input[input_len] == '\0'`
  ([implementation lines](https://github.com/bellard/mquickjs/blob/main/mquickjs.c#L11304-L11344)).
- [Elk upstream repository](https://github.com/cesanta/elk): interpreter subset,
  memory claims, and licensing options.
