# Quake 1.06 startup: EXEC and DPMI alias descriptors

Research checked on 2026-10-15 before implementation:

- [FreeDOS `task.c`](https://github.com/FDOS/kernel/blob/master/kernel/task.c),
  `ChildEnv`, appends the extra-string count word `1` and the absolute program
  path after the environment terminator. `DosExeLoader` selects the largest
  available block, caps the allocation at image + PSP + MAXALLOC (or the
  available size on overflow), and requires image + PSP + MINALLOC. CiukiDOS
  already constructs that trailer in `int21_build_env_block`; Quake requests
  MINALLOC=0028h, MAXALLOC=FFFFh and ordinary low module placement.
- [DJGPP's stub source](https://github.com/jwt27/djgpp-cvs/blob/master/src/stub/stub.asm)
  scans the environment trailer, reopens its own executable, loads the COFF
  program and enters DPMI. The pinned Quake binary contains the older
  `go32stub, v 2.00T`. Its own failure path uses exit code FFh.
- [DPMI Create Alias Descriptor, including the 0.9 erratum](https://www.delorie.com/djgpp/doc/dpmi/api/31000a.html)
  allows either a data or executable source selector. The new alias has the
  same base and limit and does not track subsequent source changes. Enforce
  the existing allocated-LDT/VM checks, but do not require executable type.

`RUNREC FAIL R0A T00` is a child's normal termination with exit code 0Ah,
reported by INT 21h/4Dh. It is neither a RUNREC stage number nor an EXEC
error. An EXEC error 10 would be printed as `RUNREC FAIL E000A`.

The supplied `926f41bd` serial log records one DPMI entry, no fault, one
termination, and this child exit code. A read-only host CPU replay of the
same bundled games image reproduces it. The pinned QUAKE.EXE is 404480 bytes,
SHA-256 `7cdb244122cc607cc6f162524bfcac60f6d11d8ca2ff07473d6cd962311161fb`.
Its COFF entry at 10A8h reaches `INT 31h/000Ah` at 10F5h with BX=DS, a data
selector. CiukiDOS's DPMI `dpmi_ldt_service` rejects it with CF set because
of `!s.code`, leaving AX=000Ah. The following `MOV AH,4Ch; INT 21h` at
10F9h/10FBh therefore exits with 0Ah before Quake's main function. The
preceding unsupported 0507h call is deliberately ignored by this CRT.

The environment, MZ allocation and PSP must be checked during the real
EXEC replay. They must not be changed merely to account for an unrelated
post-EXEC failure. This is a host diagnosis, not a QEMU qualification.

The fix removes only the executable-type restriction from INT 31h/000Ah;
allocated-LDT validation, descriptor copying and client ownership remain in
place. The host and DOS conformance tests now accept data sources and retain
an invalid-selector rejection after freeing the alias. The host LDT test
also verifies that the alias keeps its original base when its source moves.

`tests/host/dosvm_exec_test.py` assembles the production DOS personality,
shells, RUNREC and DPMI conformance probes into a temporary sparse FAT16 test
fixture. It extracts and checks the complete, unmodified Quake executable
from the vendored archive; it needs no canonical DOS or games image and
includes no PAK. It replays the 16/32-bit clients and nested children, then
launches Quake through the actual shell/RUNREC/EXEC path. Host observations
check the MZ fields, initial stack, child PSP/MCB/parent linkage/JFT/command
tail, largest-block allocation and the environment's count/path trailer.
They then check that the stub reopens that absolute path and that the CRT's
first data-alias request succeeds. Guest code and results are not patched.

Before the fix the same pinned-executable replay passes the EXEC checks,
then reports `RUNREC FAIL R0A T00` and fails. With the fix it stops after the
successful alias call, with DPMI active, one entry, no termination and no
RUNREC verdict. This establishes removal of the reproduced R0A blocker;
it does not establish full Quake startup, rendered frames or demo completion.

The lead must rebuild the canonical image and DOS probes, then qualify
`quake-qemu-t23`, `dos4gw-qemu-t23` and the `f3-vm` cases sequentially on that
same image SHA-256, preserving earlier gates. In particular, DPMI16/32 must
still record both success and invalid-input failure for row 000Ah, pass
nested EXEC and clean up their descriptors and memory. Quake must advance
beyond the early CRT and produce the video/demo evidence required by its
case; an active DPMI client alone is insufficient.

Validation: the kernel host suite ran once with
`ASAN_OPTIONS=detect_leaks=0 nice -n 19 bash scripts/test/host_kernel_tests.sh`
and exited 0 (DOS VM harness: 8110128 checks, maximum record 237 bytes).
The new fixture ran both DPMI clients and the pinned Quake replay even
though the optional prebuilt-DOSBOOT matrix was skipped in this worktree.
`nice -n 19 python3 scripts/build_kernel.py` exited 0, including its FPU/SIMD
audit, and produced `build/f0/VMM.ELF` (5078420 bytes), SHA-256
`65105494cb32d1a78d45169264af30dacc02759554a84099bc8447badea6ba14`.
Verbatim test and build output is in `build/codex/f3-28-report.md`. No QEMU,
canonical image build, systemd scope, commit, push or diary was performed.
