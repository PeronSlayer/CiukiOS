# DOS boot-sector fetch after a startup reschedule

Research checked on 2026-10-15 before implementation:

- [Intel SDM, Volume 3A](https://www.intel.com/content/dam/www/public/us/en/documents/manuals/64-ia-32-architectures-software-developer-vol-3a-part-1-manual.pdf),
  chapters 4 (paging), 6 (page-fault exception) and 20 (virtual-8086 mode):
  V86 instruction fetch uses the active CR3 page tables. Page-fault error
  `4` describes a user read with a missing translation. Reading the bytes
  through a different page directory does not prove they are executable
  through the currently active directory.
- The repository's `core/task.c` restores CR3 using `dosvm_task_cr3` on
  every dispatch. `dosvm_boot` copies sector zero to the private mapped
  frame at `0x7C00`. The worker selects that directory, then calls
  `dosvm_startup_report` before `v86_enter` establishes `continuation`.
  Startup output can reschedule explicitly. The hook currently requires
  that continuation and therefore resumes the worker in the kernel
  directory, where the guest boot page is absent.

Decision: select the worker's private directory for its entire task
lifetime. Keep the continuation requirement for TSS ESP0 and guest trap
ownership; it describes the live entry stack, not address-space ownership.
The worker is reaped before `as_destroy`, so the private directory remains
valid whenever the scheduler can select that task. No memory quota,
admission, disk cache, FAT, BIOS VM or DOS image behavior needs changing.

Merge `39915324` (f3-25) exposes this existing startup window to diagnostic
probe boots by adding `CBI_F_DIAG_VERBOSE` to startup screen reporting.
Verbose boots already had the latent window. The supplied failed run has
flags `0000116e`, successful admission and valid sector bytes, followed by
`#PF` at the first instruction with error `4`.

Both DOS payloads were rebuilt with their revision's
`scripts/build_dos_image.py`; the old sources were extracted read-only
from `git archive 0712bc59` into temporary scratch, without another worktree.
Both images are 134217728 bytes, with 512-byte sectors, eight sectors per
cluster, 73 reserved sectors, two 128-sector FATs, root LBA 329 and data
LBA 361. Their boot sector and reserved loader bytes are identical.
Only `CIUKIDOS.SYS` changes, from 50170 to 50174 bytes; both pass the ABI
and memory-layout validator with identical region segments and paragraph
counts (3136 kernel paragraphs). The FAT allocation tables are identical.
The four-byte change cannot explain a fault
before the boot sector has executed. Detailed hashes and test evidence
are recorded in `build/codex/f3-27-report.md`.

The new host regression runs production `dosvm_create`, `dosvm_boot` and
the worker on the assembled production boot sector. It requests a
reschedule during the first startup screen report, dispatches away and
back using the production CR3 hook, and makes libx86emu fetch through the
active page tables. Before the fix it executes zero instructions and
faults at `0x7C00`, vector 14, error 4. After the fix both entry jumps retire
and the first CLI traps at `0000:7C43`, vector 13. It checks diagnostic,
verbose and quiet boots, continuation-dependent ESP0, unrelated tasks
and resource cleanup. This is host CPU/scheduler replay; the lead must
qualify the rebuilt canonical image on QEMU.

The complete kernel host suite ran once, sequentially, with
`ASAN_OPTIONS=detect_leaks=0 nice -n 19 bash scripts/test/host_kernel_tests.sh`
and exited 0. The DOS VM harness passed 8110101 checks; the rebuilt real
DOS image replay passed 27156459 instructions and 215864 traps with zero
unexpected events. Its TCG model replay passed 853701 instructions and
174716 traps with zero unexpected events. Neither replay substitutes for
QEMU evidence. The lead must rebuild one canonical image and run
`f0-smoke`, `dos4gw-qemu-t23`, `vm-audio-qemu-t23` and `quake-qemu-t23`
sequentially against that image's SHA-256.

`nice -n 19 python3 scripts/build_kernel.py` also exited 0, producing
`build/f0/VMM.ELF` (5078424 bytes) with the FPU/SIMD audit passing.
No QEMU, canonical image build, systemd scope, commit or diary was run.
