## Procedure and limits

The baseline was measured before production changes, with the corrected DOOM
replay already installed: 320 column writes followed by 959 per-plane span
writes, one map-mask OUT for each (1,279/frame), native stores at stride 80,
A000/A4000/A8000 triple buffering and CRTC completion. This is a synthetic
replay shaped by the supplied research and its measured OUT count, not a
captured execution of a commercial game. Wolf uses the existing real-mode
compiled-scaler instruction replay (near/mid/far masks), plus mode-1 latch
copies. Each timed replay runs 120 frames, checks independent expected plane
bytes outside its timed region, and uses production mapping/presenter code.

All builds/tests ran at `nice -n 19`, sequentially. The baseline and final
kernel host suites used `ASAN_OPTIONS=detect_leaks=0`: LeakSanitizer cannot
run under this sandbox's ptrace restrictions. AddressSanitizer and
UndefinedBehaviorSanitizer remained enabled. No QEMU, image build, commit or
diary entry was made. Final focused rechecks followed the last burst/port
accounting and fill-loop refinements.

The host substitutes page tables, CR3/TLB operations and CPU exception entry;
its clock seam supplies monotonic nanoseconds. These numbers include host
instrumentation and sanitizer work. They are neither a clocked P3 model nor
T23 TSC measurements and do not establish game fps or monitor CPU share.
The original measured T23 sample remains in the supplied research.

DOOM retained about 1,279 plane selections/frame and zero aperture faults.
Repeated dirt of a page during different columns is now retained once per
plane/page until presentation: 1,279 harvests and 2,251 page publications
became one harvest and 16 publications. The per-frame harvest clock fell
from 153.180 µs to
0.236 µs on this host. Active plane
swaps use one CR3 reload rather than sixteen individual remappings; a
CRTC flip does not scan PTEs or publish pending plane damage.

Final host port record:

```text
ports=doom-mode-y map_mask_writes_per_frame=1279.00 handler_ns_per_write=190.415 remap_ns_per_swap=121.430 projected_ports_percent_at_35fps=0.852
```

The projected percentage is just 1,279 host handler timings × 35/second,
with no exception/TLB/compositor cost; it is not the T23 acceptance result.
Host replay time changes little for DOOM and the far Wolf scaler because
the host does not execute real exception or TLB flush instructions. Near/mid
Wolf still needs one first fault per strip, as in the prior burst path.
Presenter and latch-copy work improved independently.

New vectors verify full-span rejection without PTE changes or ownership
changes, active/inactive/clean flush counts, D/A masks, the 1,279-write DOOM

high halves; word/dword latch copies keep the scalar fallback.

## Remaining lead evidence

The lead must build the canonical image, run `f3-vm` video cases and
`vm-window`, then qualify the T23: DOOM ≥35 fps and monitor <20% wall time,
Wolf3D ≥70 fps, port-trap timing and presenter timing. Also compare one CR3
reload with sixteen INVLPGs on the actual P3. No image SHA is claimed here.

The accepted direct native-read/latch limitation is explicit in the design:
GC04-driven reads select the right shadow, but a writable PTE cannot return
a different plane on arbitrary native reads or load all four VGA latches.
Latch-dependent modes remain trapped. `vm_perf_wall` exposes the off-CPU
remainder, rather than attributing it to the VM monitor; distinguishing
native composition, other tasks and idle requires lead-side evidence.
