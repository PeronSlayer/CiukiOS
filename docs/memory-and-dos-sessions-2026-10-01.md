# Full profile: RAM and DOS sessions (1 October 2026)

## Sources and decision

- [Microsoft XMS 3.0 specification](https://ps-2.kev009.com/basil.holloway/ALL%20PDF/Microsoft_XMS_3%5B1%5D.0_Specification.pdf): DOS programs discover extended-memory capacity through XMS, including the 32-bit `AH=88h` query. The conventional 640 KiB arena is a separate constraint; giving a machine 128 MiB does not make a real-mode program's conventional arena 128 MiB.
- [Microsoft's Windows 95/98 VMM description](https://learn.microsoft.com/en-us/archive/msdn-magazine/2000/july/under-the-hood-happy-10th-anniversary-windows): Windows 9x runs DOS sessions in virtual-8086 machines with virtualized interrupts and devices. The presence of VMs in CiukiOS is therefore consistent with the chosen model. Windows NT's NTVDM is a different architecture and is not the model for this work.
- [Pinned upstream Jemm source](https://github.com/Baron-von-Riedesel/Jemm/tree/e96bb6bb80cbdc3e6585544db79a6b133a5566dd) and `third_party/jemm/UPSTREAM.json`: JemmEx combines the V86/UMB role with XMS. We build that exact source with the existing CiukiOS V86/session adaptations, and preserve its provenance.
- [Microsoft's MS-DOS system-call reference](https://github.com/microsoft/MS-DOS/blob/main/v2.0/source/SYSCALL.txt): an `INT 21h/AH=48h` request that cannot fit returns the largest free conventional block in `BX`. A COM program must first shrink its own DOS block before this number describes the memory other programs can allocate.
- [Microsoft MS-DOS 3.3 Programmer's Reference](https://www.pcjs.org/documents/books/mspl13/msdos/dosref33/): DOS `EXEC` creates a child PSP and returns to its parent through the saved termination context; the parent process and its memory ownership must remain coherent while the child runs. For this reason the forked DOS session must not simply discard ancestor PSP blocks to inflate a free-memory number.
- [Microsoft Windows 95/98 conventional-memory guidance](https://ftp.zx.net.nz/pub/Patches/ftp.microsoft.com/MISC/KB/en-us/134/399.HTM): the compatibility metric is the largest executable program size; conventional-memory residents and fragmentation reduce it even when extended memory is plentiful. Measure the actual resident MCB layout before changing a limit or making a resident movable.
- [Microsoft's MS-DOS system-call source](https://github.com/microsoft/MS-DOS/blob/main/v2.0/source/SYSCALL.txt) defines `SetBlock` (`AH=4Ah`) and `KeepProcess` (`AH=31h`): a resident's live paragraphs cannot be reclaimed merely by shrinking its advertised size. [FreeDOS's MCB definition](https://github.com/FDOS/kernel/blob/master/hdr/mcb.h) records a block's owner PSP and size; our fork compactor checks both before moving the two known COM residents.

Before this change, the full kernel advertised its own XMS service but exposed at most 64 MiB, while the V86 monitor reserved a fixed 32 MiB region. The full image now leaves the XMS multiplex service to JemmEx and starts it without that fixed upper-memory reservation. The existing CVSESSION DOS window, scheduler, device emulation and per-VM low-memory isolation remain in place. DOS programs obtain extended memory through the standard XMS API; a program limited to conventional memory still needs its own compatible extender or memory strategy.

The legacy internal XMS implementation remains available to non-full builds through `CIUKIDOS_EXTERNAL_XMS=0`. The main full profile enables `CIUKIDOS_EXTERNAL_XMS=1` and ships `VM/JEMMEX.EXE`. The external manager is loaded by `VMSTART` during the desktop boot.

## Measurement and validation

`scripts/qemu_test_memory_capacity.py` boots copies of the canonical full HDD image with 128 and 256 MiB of guest RAM. Its DOS COM probe queries XMS 3.x `AH=88h`, then uses `AH=89h` to allocate a block one MiB smaller than the reported largest block and `AH=0Ah` to free it. This checks usable capacity as well as the reported number. Observed free XMS:

| Guest RAM | Free XMS | Difference |
| --- | ---: | ---: |
| 128 MiB | 125.0 MiB | about 3 MiB |
| 256 MiB | 253.0 MiB | about 3 MiB |

Before resident compaction, `AH=48h` reported a largest conventional block of **484 KiB in the system DOS prompt** and **482 KiB in a forked DOS VM**. With JemmEx moved high and the fork's DOS residents compacted, the same probe reports **487 KiB in the system prompt** and **544 KiB in a forked DOS VM** at both 128 and 256 MiB of guest RAM. The installed-RAM increase changes XMS capacity, not the first 640 KiB DOS address space. The fork's gain is from removing desktop memory and placement gaps in its private conventional arena.

The [Jemm manual for the pinned version](https://github.com/Baron-von-Riedesel/Jemm/blob/e96bb6bb80cbdc3e6585544db79a6b133a5566dd/Readme.txt) says `NOHI` keeps Jemm's resident part out of upper memory. Removing it initially made `JLOAD` report `Jemm not installed`: CiukiOS's device query rejected its upper-memory header. The query now accepts only the configured `CD000h..EBFFFh` UMB addresses for Jemm's device header and handler, and the full boot gate confirms `JLOAD` and CVSESSION start. JemmEx moves high and adds about 3 KiB to the system prompt's largest conventional block.

The pinned [protected-mode initializer](https://github.com/Baron-von-Riedesel/Jemm/blob/e96bb6bb80cbdc3e6585544db79a6b133a5566dd/src/INIT.ASM) maps the UMB at `CD00h` and reports `resident part moved high, seg=cd00`; the [real-mode loader](https://github.com/Baron-von-Riedesel/Jemm/blob/e96bb6bb80cbdc3e6585544db79a6b133a5566dd/src/JEMM16.ASM) exits without a low DOS TSR when that succeeds. A physical-memory dump of the remaining `2099h..24EBh` resident block matched the built `SYSTEM/LFN.COM` from its first instruction through its code. This resolved the earlier mistaken attribution of that roughly 17 KiB block to JemmEx. The other low resident was `AUXSTACK.COM` at `2049h..2099h` (matched to its shipped binary); the desktop root PSP occupied roughly 58 KiB.

The fork now rebases its launcher into the gap created by shrinking the copied desktop root PSP to 256 bytes. It copies the two known resident COM images (`AUXSTACK` and `LFN`) into that gap, changes only their private VM interrupt-vector segments, and releases their retired low blocks through the existing fork-only owner-aware free call. Before `EXEC`, it restores the prior DOS allocation strategy. The kernel's new fork-only `F1h/4Ah` branch uses the existing `SetBlock` implementation with the selected ancestor PSP as its temporary allocation identity. The system VM's PSP and memory are untouched. The fork keeps V86 isolation, consistent with [Windows 95/98 DOS sessions](https://learn.microsoft.com/en-us/archive/msdn-magazine/2000/july/under-the-hood-happy-10th-anniversary-windows).

The diagnostic before compaction found the system prompt's first PSP block at `117Fh..2010h` (about 58 KiB). In the old fork, after unused ancestor allocations were removed, the first PSP block still occupied `117Fh..2652h` (about 83 KiB) and the executing launcher started at `2652h`; the free tail started at `2670h` and ended at the BIOS boundary `9FC0h`. The XMS 3.0 `AH=10h` UMB request successfully returned segment `CD00h` in that fork. [The XMS 3.0 specification](https://ps-2.kev009.com/basil.holloway/ALL%20PDF/Microsoft_XMS_3%5B1%5D.0_Specification.pdf) distinguishes UMB below 1 MiB from conventional and extended memory. The diagnostic led to compacting the copied fork's PSP and residents in conventional memory.

The earlier UMB-launcher prototype reached only 488/491 KiB because the actual `LFN.COM` and `AUXSTACK.COM` blocks remained above the new PSP. The implemented fork uses the DOS allocator's best-fit strategy temporarily: CiukiDOS's first-fit branch deliberately carves allocations from the high edge of a gap, which had placed the moved residents around `1BA8h..1FFAh` and left the executable limit near 500 KiB. Best fit places the root PSP at `1180h..1190h`, AUXSTACK at `1191h..11E0h`, LFN at `11E1h..1632h`, the rebased launcher at `1633h..1718h` in the diagnostic build, and a continuous free tail to `9FC0h`. The shipped no-debug build yields **544 KiB** inside the `MEMCAP.COM` child. This is a measured gain of about 62 KiB over the old fork path; it does not claim a 550 KiB child block.

The full image still logs JemmEx's warning that BIOS memory was found in the forced `I=CD00-EBFF` interval. The configured interval and upper-memory handler remain bounded; QEMU XMS and CVSESSION gates pass. Real hardware must still qualify that UMB interval before this profile can be considered physically validated.

The test requires at least installed RAM minus 8 MiB at each size and at least 120 MiB growth between the two. The full HDD boot smoke, full CD boot smoke at 128 and 256 MiB, and `scripts/qemu_test_full_dos_memory.py` also passed with the JemmEx profile, covering DOS allocation, a forked VM, and `COMMAND /C` and `/K`. The CD was rebuilt after the resident-copy correction and passed its final 128 and 256 MiB boot smokes. Both final CD logs recorded `VMSTART: ready.` before desktop readiness.

The final M4 QEMU integration report at `build/tests/memory-m4-20261002-final2/report.json` passed: Doom ran in a DOS window alongside Files, a second `COMMAND.COM` window opened, focus and keyboard routing worked, and closing the second VM left the first running. An earlier run sent Enter immediately and launched a mistyped `\CCOMMAND.COM`. A diagnostic screenshot captured the Run field still displaying only `\COMM` immediately after all keys were injected, showing that guest input and repaint lagged the test. The harness now waits before Enter; repeated M4 runs passed. This supports a test timing race, but does not prove every physical keyboard path is reliable.

The final fork also ran the shipped `AUXCHECK.COM` through the relocated video stack hook and the repository's `LFNTEST.COM` probe through the relocated long-name hook. Both passed in a disposable copy of the final HDD image (`build/tests/fork-residents-20261002-final`). The resident copy length was corrected to the MCB payload size before these runs; an MCB size already includes the PSP and program image.

The canonical Windows portable ZIP was rebuilt from the final HDD image. ZIP integrity, the manifest image SHA-256, JemmEx presence and absence of all eight configured private guest paths were verified in `build/tests/release-integrity-20261002.json`; archive SHA-256 is `baaf798efeec69c8eedf9241c04e65904f14b9c1ac09126b052bd881fafa94fd`. Its Windows launcher was not run on Windows. After correcting the resident copy length to the MCB payload size, the rebuilt image passed the 128/256 MiB XMS capacity probe and parent/forked DOS memory and `COMMAND /C`/`/K` gates.

These QEMU measurements show that the 64 MiB cap and fixed 32 MiB reservation no longer limit the tested full profile. They do not establish compatibility for every DOS game, every memory extender, physical hardware, or Windows 98 applications. Those remain separate compatibility gates.

## Linux host build safety

The host has 14.8 GiB RAM and 14.8 GiB zram swap. `systemd-oomd` killed the VS Code cgroup twice on 1 October at 19:24:40 and 19:58:15, when both RAM and swap exceeded 90%; the second event coincided with an unrestricted full build launched from VS Code. Heavy build and QEMU commands should run in separate `systemd-run --user --scope` units with memory limits as specified in `AGENTS.md`. A VS Code extension-host file search also traversed the very large `build/` tree; `.vscode/settings.json` now excludes it through `files.exclude`, which the [VS Code `workspace.findFiles` API](https://code.visualstudio.com/api/references/vscode-api) uses by default.
