# S3 SuperSavage support research

Research completed 2026-10-07 for the ThinkPad T23 graphics path. This note records what the established upstream drivers do and what CiukiOS would need to reproduce. The local hardware target is PCI vendor/device `5333:8c2e`, named SuperSavage IX/C SDR by the Linux PCI ID table and Xorg's driver. It is a member of the SuperSavage mobile family, not a Savage4 device.

## Upstream evidence

The Xorg `xf86-video-savage` 2.4.1 driver recognizes PCI ID `0x8c2e` as `PCI_CHIP_SUPSAV_IXCSDR`, maps the PCI MMIO and framebuffer BARs, and locates the BCI command aperture at `MMIO + 0x10000`. It provides 2D acceleration and Savage-family 3D support. Its manual says all listed Savage chips other than Savage2000 support 2D/3D acceleration. The driver explicitly disables both vertex DMA and command DMA on SuperSavage, while retaining BCI acceleration. The Mesa 7.11.2 Savage DRI driver likewise disables vertex DMA for `S3_SUPERSAVAGE`; it still has hardware primitive paths using client vertex buffers. Therefore, lack of DMA does not mean that 3D is software-rendered.

The Linux 6.2 legacy Savage DRM implementation validates and dispatches both DMA and client-vertex primitive commands. For non-Savage3D-family chips, which includes SuperSavage, it uses the S4-style draw and index encoding. It accepts triangle lists, strips and fans, validates vertex layouts and emits the vertices through BCI. This is direct evidence of a hardware triangle command path suitable as a protocol reference, though the kernel's “DMA” helper can stage commands and flush them over BCI; it does not establish that a DOS process can use the path safely without host support.

## Relevant command path and chip distinctions

The shared BCI register command is `0x96000000 | (count << 16) | register_index`, followed by register values. The draw primitive command is `0x80000000 | (primitive << 25) | (skip_flags) | (vertex_count << 16)`, followed by vertex data. Triangle-list primitive is `0`, strip `1`, fan `2` in the DRM UAPI (encoded after shifting left 25). The indexed-primitive opcode is `0x88000000`. Vertex data is a packed sequence of 32-bit words; the DRM client-vertex path derives its size from skipped fields and the selected chipset family. It splits submissions at 255 vertices. For the non-Savage3D layout, the full vertex is ten dwords: mandatory X,Y followed by optional Z,W,C0,C1,S0,T0,S1,T1 fields. For an untextured X,Y,Z,C0 submission the skip mask is `0xFA` (W,C1,ST0,ST1 skipped), subject to verifying the actual packed color and coordinate representations against the Mesa vertex setup before use. The BCI wait opcodes are `0xC0000000` plus `0x00010000` for 3D idle or `0x00020000` for 2D idle.

The 2D BCI uses the same MMIO command aperture. Xorg's solid fill path builds a rectangle command from `RECT | RECT_XP | RECT_YP | DEST_PBD_NEW | SRC_SOLID`, sets its ROP and optional color, then sends descriptor-low, descriptor-high, optional color, packed XY and packed WH words. XY is `(y << 16) | x`; WH is `(h << 16) | w`, with 12-bit coordinates/dimensions. The generic rectangle opcode is `0x48000000`; line is `0x5c000000`. The Linux driver records a 32-dword hardware FIFO and, for this non-Savage3D family, polls ALT_STATUS_WORD0 at MMIO `0x48c60` with used-count mask `0x001fffff`; it waits until used entries are at most `COB_size + 32 - n`. With no command overflow buffer, this is `32 - n`. Linux bounds the poll at one second. Xorg also polls for FIFO room before each BCI batch. A production implementation must preserve synchronization rules and bounded timeout recovery rather than treating MMIO as ordinary framebuffer memory.

The Xorg mapping code is especially important for selecting the target apertures: for SuperSavage it uses PCI BAR0 as the MMIO register base (SuperSavage uses the `S4` MMIO base offset, zero), BAR1 for framebuffer VRAM, and BAR2 for the tiled-addressing aperture. The BCI dword write window starts at BAR0 + `0x10000`. These are PCI resources to discover from this device's config header; a port must not hard-code addresses or infer the mapping from a different Savage card. Xorg requests 5 x 16 MiB for a single-head aperture and 2 x 16 MiB for dual-head, then clamps that request to BAR2's probed size. It uses BAR2 as the CPU-visible linear view of VRAM surfaces configured as tiled; do not infer a `+64 MiB` slot without checking the BAR size and chipset mapping.

For a minimal untextured 3D proof, use explicit 16-bit RGB565 color surfaces and a separate 16-bit depth surface, with tiled storage, byte offsets and pitches reserved in VRAM. The DRM init structure has independent front/back/depth bpp, offset, and pitch fields and rejects unsupported framebuffer/depth sizes outside 16 or 32 bpp. Mesa sets DESTCTRL width-in-tiles to `ceil(width/64)` at 16bpp or `ceil(width/32)` at 32bpp, and stores the selected front/back surface offset in 2 KiB units (`offset >> 11`). ZBUFOFF similarly holds the depth offset and tile width, with a depth select based on 16/32-bit Z. S4-compatible 3D state register indices are ZBUFCTRL `0x32`, ZBUFOFF `0x33`, DESTCTRL `0x34`, DRAWCTRL0/1 `0x35`/`0x36`; in this family the scissor bounds live in the two draw-control registers. State must match the actual viewport, tile dimensions, surface offsets, color format and Z mode. This is not a safe place for guessed magic values: Mesa's `savage_3d_reg.h` defines packed fields and `savagestate.c` computes them; complete Xorg GBD setup also includes stream/VGA register setup. The CPU accesses tiled storage through the BAR2 addressing aperture. A backend needs an upstream-validated way to expose/copy a rendered back surface to scanout; a linear LFB write path does not create a valid 3D destination.

Do not copy Savage4 setup values blindly. Xorg has a distinct `SavageSetGBD_PM` path for SuperSavage: it enables BCI with bit 0 (`BCI_ENABLE_TWISTER`), while the Savage4 path uses bit 3 (`BCI_ENABLE`). The GBD tile-format meanings also differ: SuperSavage follows the PM/Twister destination-tiling encoding, while Savage4 uses its own 16/32-bit tile encodings. For the PM/Twister tiled CPU aperture, Xorg uses tile-surface registers `0x48c40` through `0x48c50` at four-byte steps; a single-head framebuffer uses surface register 0 and dual-head uses surface register 1. At 16bpp it derives the surface tile-width field from `(lDelta / 2) >> 6` and sets the 16bpp surface-format bits; at 32bpp it uses `(lDelta / 4) >> 5` and the 32bpp format. The DRM enum puts `S3_SUPERSAVAGE` outside its `S3_SAVAGE4_SERIES` macro, but its “not Savage3D family” draw dispatch selects the S4-style primitive layout. That is a command-format compatibility choice, not a claim that these chips share initialization or display registers.

Xorg maps PCI BARs through the host OS PCI mapping API. The VGA-compatible framebuffer/LFB row interface in CiukiOS does not provide this MMIO mapping or BCI FIFO access. The current DOS V86 renderer therefore cannot reach the hardware command path through its existing row API. Since local unreal-mode access is prohibited, a real acceleration port needs a narrowly scoped host/CVSESSION service that discovers and maps the approved Savage BAR, exposes ordered 32-bit BCI writes and bounded FIFO/status waits, and owns synchronization/timeout recovery. The DOS-side renderer must then initialize verified descriptors and the tiled-surface aperture, 2D state, and 3D color/depth/viewport state before submitting triangles. A direct hardware 2D rectangle/line path is a smaller first milestone; a TinyGL or CPU raster fallback must be described as software rendering, not hardware 3D.

For the ThinkPad display issue, keep mode selection separate from acceleration. Xorg's driver recognizes all SuperSavage IX variants and has dedicated mobile display/stream handling. The screen mode should be constrained to the actual panel and BIOS/VBE modes reported by the T23, then tested at that mode; source support for the chip alone does not guarantee every panel timing is valid. Fixing the mode can address clipping/scaling and improve throughput by reducing pixel count, but does not itself enable acceleration.
