# g32b: users, logon and passwords — defects and completion

- **Written:** 2026-10-26 by the lead. Implementer: Codex gpt-6.1-sol, effort high. Base: main 17fd29b2a. Trigger: the owner asked whether the user/logon system really works. Lead audit of G32 (`docs/design/users-and-logon.md`, `apps/desktop/users*.c`, `logon.inc`, `apps/control/users.inc`): the local core is real (salted PBKDF2-HMAC-SHA-256 verifiers, opaque desktop-owned gate, per-profile folders) but it has only host evidence, one defect that can disable account management for good, one option that promises a lock it never performs, and Win32 programs that ignore the logged-on user.

## Model (unchanged, owner decision 2026-10-22: Windows 9x model everywhere)
Windows 98 logon selects a profile; it is not access control (Resource Kit ch. 7 `wrkc07_3.htm`, ch. 9 `wrkc09_4.htm`, ch. 18 `wrkc18_2.htm` in build/rskt). Cancel at logon gives the default profile; FAT has no permissions; there is no administrator. Keep that. Do not add NT tokens, ACLs or an administrator role. Copy that tells the user what protection exists must be exact (no "secure" claims).

## Scope
1. **Stale lock (defect).** `apps/desktop/users_io.c:63-71` creates `/system/settings/users.lock` with O_EXCL and removes it at the end. A crash or a forced power-off during a mutation (the owner had to force power-off on the last trial) leaves the file, and every later create/delete/change-password/policy call returns EBUSY for ever; there is no recovery. Make the lock recoverable: record the owner (pid and boot identity or boot time) in the lock, break a lock whose owner is not alive in this boot, keep mutual exclusion between the desktop worker and the Control Panel applet, and keep the atomic temp+fsync+replace save. Host tests: leftover lock from an earlier boot, from a dead pid, live contention.
2. **Screen saver password (defect).** The Users/Passwords page offers "Password protection for screen saver / Lock" (`apps/control/users.inc:75`, flag USERS_LOCK) but dismissing the saver (`apps/desktop/client.c:1204-1221`) never calls `desk_session_lock`; only Start > Lock does. Wire it as Windows 98 does: when a named profile is logged on and the option is set, input that dismisses an idle-started saver (or SC_SCREENSAVE) opens the password gate before any desktop pixel is shown; the saver Preview never asks for a password; Cancel keeps the session locked; monitor-off/DPMS wake goes through the same gate. Research and cite the Windows 98 behaviour (Display Properties > Screen Saver > Password protected; SCRNSAVE.SCR/ScreenSaverProc docs) before coding. Window-model scenario rows for each case.
3. **Password on resume (PW-8).** Windows 98 Power Management > Advanced has "Prompt for password when computer goes off standby". Add that option to the Power page (`docs/design/power-policy.md`, G11) and lock on resume from Stand by through the same gate when a named profile is logged on. Host test through the existing resume notification path.
4. **Win32 identity and folders.** `apps/w32srv/registry.c:396-398` answers GetUserName with "Ciuki" whatever the logon. Research Windows 98 behaviour (GetUserName, HKEY_CURRENT_USER loaded from the profile's USER.DAT when profiles are enabled, SHGetSpecialFolderPath/CSIDL for Personal, Desktop, DesktopDirectory, Programs, Start Menu, Favorites, AppData, Recent, SendTo, Templates under the profile) and implement it: w32srv learns the current profile from the desktop through an existing internal channel if one fits (no new public ABI unless unavoidable; if abi.h changes, follow the ABI oracle rules), GetUserName returns the logged-on name (and the Windows 98 answer when nobody logged on), HKCU is per profile (separate hive file under the profile root, created from the default hive on first logon, flushed on logoff), and the shell folder APIs and the `User Shell Folders` keys point into the profile. Running Win32 programs keep the identity they started with; a logoff ends them first (existing G3 path).
5. **Evidence for the lead.** Host tests for every item and the existing suites green: `tests/host/desktop` (window model, users, control), `tests/host/win32` (registry, shell, advapi32), the users/control tests named in the G32 report. Write in the report an exact QEMU checklist the lead will run with `qa_drive.py` (create a user with a password, enable logon, restart, wrong password, right password, Cancel = default profile, files on the profile Desktop, Lock, saver wait 1 minute + dismiss = gate, Log Off, leftover users.lock from a forced power-off, a Win32 program reading GetUserName and My Documents).
