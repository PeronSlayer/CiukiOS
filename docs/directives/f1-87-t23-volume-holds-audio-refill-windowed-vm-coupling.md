Host test: a hold without a tag fails the test.
B. **Bounded holds for readers and the log writer.** Research first (Windows 98 IFS Manager/IOS: the volume lock is per request, transfers do not hold the namespace while the device works; cite the Resource Kit chapter and the DDK text you use in the report). Then: a read of N blocks holds the volume only for metadata (cluster chain resolution) and releases it while the device transfers; a multi-block transfer is issued as block requests that wake waiters between them; `log_write` and `commit` of the storage writer write under a budget (f1-83/f0-42 writeback budget) and never hold the volume across more than one budget slice; the `dosvm mkdir` 441 ms hold is split the same way. Acceptance on the host model: no hold above 20 ms with the T23-like service time model (`svc_max_ms=111`) in a replay of the trial's request mix (write the replay fixture from the facts above).
C. **Audio refill never waits behind a desktop read.** The refill task's reads take the reader-priority path of C3 ahead of normal readers (the desktop's resource reads are normal); Music's decoded buffer covers at least 2 s so a 1.5 s hold cannot reach the transport. `device_overrun task=audio-refill` must disappear from a host replay of the trial's hold pattern; add the test.

## Amendment 1 (lead, 2026-10-21): design for B (bounded logical holds) and the C replay; second Sol session

The first session delivered A, D, E, F, G and parts of B and C (commit 178832fe). B fails the acceptance: the physical namespace/volume mutexes no longer span device work, but the **logical FAT mutation guard** (`mutating`) still spans the whole operation; cold replay maximum 999 ms against the 20 ms limit. The lead reviewed the problem and fixes the design (binding; cite the Windows 98 IOS/IFS Manager and VFAT behaviour you use, and the C2/C3 rules of `docs/design/resource-management-win98.md`):

**B design: reserve, transfer, publish.** Every FAT mutation (file extend/write, log append, commit, mkdir, rename, unlink) becomes a three-phase transaction:
1. **Reserve (under the guard, bounded):** resolve the chain, allocate the clusters needed by the whole operation and mark them in an **in-flight reservation set** (a small per-volume table or bitmap of clusters reserved but not yet published), prepare the new FAT entries and directory entries in a private transaction record (in memory, bounded size; a long append is split into several transactions of at most one budget slice of blocks). No device I/O in this phase. Guard hold ≤ 1 ms in the host model.
2. **Transfer (no guard):** the data blocks go to the block layer with the writer's budget and reader fairness (f1-83/C3); readers run concurrently and see the pre-transaction state; concurrent allocators skip reserved clusters; a crash here leaves orphan clusters that the existing fsck/mount-time scan reclaims (document it; add a test that the in-flight set is not persisted and reservations are released on failure).
3. **Publish (under the guard, bounded):** write the FAT entries and directory entries of the transaction to the cache (metadata blocks only, already in the cache or fetched in phase 1), release the reservations, and let the metadata writeback follow the writer's budget. Guard hold ≤ 1 ms in the model; a publication that needs more than one metadata block is still one guard section because it only touches cached blocks.

Lifetimes: path/node borrowed references taken in phase 1 are either pinned for the transaction's life (pin count on the node, released at publish or abort) or revalidated at publish by generation; choose one and test the rename/unlink races (a concurrent unlink of the target between phases must abort the publication cleanly, never publish into a dead node). The storage writer's `log_write` and `commit` use the same machinery: one transaction per budget slice, publication after each slice, so no reader waits longer than one slice (≤ 20 ms with the T23 service model `svc_max_ms=111` only if the slice is one block; size the slice by service time, not by block count). `mkdir` is one transaction.

Acceptance (unchanged): T23 service-time model replay, no logical hold above 20 ms; plus the new tests (reservation isolation, abort paths, crash-cut orphan reclaim through the existing fsck classification, rename/unlink races).
