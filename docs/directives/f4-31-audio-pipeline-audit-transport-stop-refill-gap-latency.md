## Required

1. **Research and write the audit first** (`docs/validation/f4-31-audio-audit.md`): primary sources — Intel ICH AC'97 controller programmer's reference (BDL, LVI/CIV/PIV, DCH, FIFOE, CELV, the 32-entry descriptor ring), AC'97 2.3 codec spec (rates, power), Linux ALSA `intel8x0` (period/buffer handling, underrun recovery, `snd_pcm_period_elapsed`), ALSA PCM design (period/buffer/latency, xrun recovery), PulseAudio's timer-based scheduling notes (as a design reference only), DOSBox/DOSBox-X mixer design for the SB16 timeline, ESS Maestro-2E programming reference (E500 target), Sound Blaster 16 ISA DMA programming (desktop baseline), Intel HD Audio spec (2004-class targets). Compare each with the repository and list the gaps with file:line.
2. **Transport lifecycle.** The backend must be running whenever any source (native stream or attached VM) has data, and must restart automatically after an idle stop, an underrun halt or an error: a native `write()` on a stopped transport starts it before the write returns; a VM source that pauses (DMA masked, DOS prompt) must not keep the transport in a state that blocks native streams; every stop/start/halt/underrun is one `[audio]` record (protected class) with the reason and the counters. Host test: VM plays → idles → native stream starts → sound within 50 ms; VM resumes while the stream plays → both mixed.
3. **Refill robustness.** Decide the lead and period sizes from measurements, not constants: the refill worker's maximum observed gap on the T23 (113 ms during a native full-screen switch; 134 ms display-watchdog stretches now bounded by f1-80) must be covered by the published lead with margin (e.g. lead 12–16 periods when a VM is attached, 24 when idle; or adaptive: grow the lead after each late service, report `lead_periods` in the record); the worker runs at `P_DEVICE` with a bounded 2 ms service and is woken by the BDL interrupt, not only by the 4 ms deadline; an underrun never silently stops the transport: it is counted, the DMA is restarted within one period, and the record names the task that held the CPU (from `stretch_max_ms`).
4. **Latency budget.** Measure end to end on the host model and document for the T23: `write()` → DAC = ring position + lead; target ≤ 60 ms for native streams, ≤ 30 ms for the VM source; the music player's prefill (`player.c` queued/position) must not add more than one period; `AUDIO_GET_STATUS` reports `latency_frames` so the player can show accurate position.
5. **Resampling quality and cost.** Replace per-frame linear interpolation for 44.1 → 48 kHz with a windowed-sinc or at least a 4-tap cubic in integer math if the cost fits (measure µs per period on the host at `-O2`; the T23 budget is ≤ 2 % CPU); keep linear as a fallback for low-power targets; document the choice.
6. **Backends for every target.** The contract must define one backend interface (start/stop/halt/resume/position/period IRQ) implemented by: ICH AC'97 (done; fix anything the audit finds), ESS Maestro-2E (E500; implement the driver or a precise plan with the register sources), SB16 ISA (generic 1998 desktops; the DMA/IRQ path already modelled for the VM), HD Audio (2004 desktops; plan). QEMU twins: AC97 (present), ES1370/SB16 devices exist in QEMU — add host/QEMU coverage where a device exists.
7. **Diagnostics for the next trial.** A protected `[audio] transport …` record every 5 s while running (published, retired, halts, underruns, max gap, lead, sources, rate) and at every state change; the H page gains a "Audio 10 s" item: tone through the real backend measuring underruns, IRQ cadence and lead.
8. Host coverage: `bash tests/host/audio/run.sh`, `ASAN_OPTIONS=detect_leaks=0 bash scripts/test/host_kernel_tests.sh`, desktop music tests, `python3 scripts/build_kernel.py`. Report `build/codex/f4-31-report.md` with the audit, the decisions and before/after measurements.
