## Amendment 1 (lead review, 2026-10-20 09:15): delivery accepted, CD-audio transport decided

The delivery (worktree `wt/f5-12b`, Claude Opus session, report `build/codex/f5-12b-report.md`, proposed amendment `build/codex/f5-12b-amendment.md`) is accepted as partial: MCI core (string and command interfaces, aliases, auto-open, notifications, Windows 98 error codes), `waveaudio` (PCM and ADPCM through msacm32 into the f5-12A mixer), `sequencer` (SMF 0/1 and RMID through `midiStream`), `avivideo` as `mciavi32.dll` with DrawDib and the MCIWnd subset, msacm32/avifil32 extensions, `w32-media-qemu-t23` written unrun; 203 Win32 tests. Decisions:

1. **CD audio: digital path primary, analog fallback explicit.** The digital path (ATAPI READ CD 0xBEh, 2,352-byte CD-DA sectors, one reader thread per playing device, mixed at 44.1 kHz through the f5-12A mixer) is the production path: it works on every drive that reports "CD-DA Commands Supported" and needs no analog cable, which the owner's T23 and most assembled PCs of the era may lack or have unrouted. The analog path (PLAY AUDIO 47h/4Bh, READ SUB-CHANNEL 42h) is implemented as an explicit fallback selected per drive when the digital read fails or the drive reports no CD-DA support, mirroring the Windows 98 CD player's "digital playback" option; both paths are tested with the mock transport.
2. **Interface: versioned devctls on `/dev/media`**, addressed by optical slot as proposed; no new device node. The owner's F4 contract keeps `/dev` as a fixed node list.
3. **Ranges touching a data track** are refused before any packet (`MCIERR_OUTOFRANGE` at the MCI layer, `EINVAL` at the devctl), as Windows 98 refuses them.
4. **Audio-only discs are "ready"**: `atapi_ready` accepts a disc whose first track is audio for the media node (not for mounting); the F4 optical state machine records `audio_only=1`, AutoPlay offers the CD player as Windows 98 does, and no file system is probed.
5. The remaining questions: msvfw32 resolving GDI/USER/winmm by name on first use is accepted (recorded as a load-order decision); `play fullscreen` as a screen-sized window with integer scaling is accepted (the presenter lease is for DirectDraw); the sequencer omissions and the SDK ambiguities are accepted as recorded.
6. **Continuation f5-12B2** (`wt/f5-12b2` from main after this merge): the kernel side (devctls, READ CD and PLAY AUDIO packet paths in the optical driver, per-drive capability from MODE SENSE page 2Ah), the `cdaudio` MCI device, the CUE/BIN fixture format with synthetic tracks, the mock-transport tests, the `w32-media` guest probe. Authority adds `src/kernel/drivers/` (optical driver CD-audio commands only) and `src/kernel/fs/media` (devctls). The Quake CD music (owner trial 2026-10-19-02: "Quake gira ma senza musica") is the acceptance scenario once the DOS side also routes MSCDEX audio calls to the same path (a note for f3's owner, not this directive).

## Amendment 2 (lead, 2026-10-21): findings of the Codex read-only cross-review of the delivery (e9cc125b); "inherited" defects of the earlier partial merge are in scope

Apply this amendment only. Sources to cite: Microsoft `MM_MCINOTIFY` and `MCI_OPEN` documentation, the Microsoft RIFF update (MS ADPCM coefficient table, pp. 22–23), MMC-3 §5.17.

1. **P1 — wave/AVI teardown frees buffers still owned by the mixer** (`sdk/win32/audio/mciavi.c:249`, `mciwave.c:199`): cleanup ignores reset/unprepare/close failures and frees PCM buffers and headers; `wa_reset` can refuse when the callback queue is exhausted. Retain handle, headers and buffers until reset and close succeed, deferring through an owned pending-cleanup object as the CD path does; add the exhausted-callback-queue teardown test.
2. **P1 — `MCI_WAIT` dereferences a device after releasing its lifetime lock** (`mci.c:592`, `mci.c:459`): `default_yield(d)` reads `d->break_key` unlocked while another thread may close and free `d`. Snapshot the yield inputs under the lock and pass values; use an instance generation for the identity recheck; verify with a real two-thread harness.
3. **P1 — DrawDib palette range check overflows** (`sdk/win32/codecs/drawdib.c:266`): `start + count > 256` wraps for large arguments and allows an out-of-bounds write. Validate `start <= 256` and `count <= 256 - start` after rejecting negatives; `INT_MAX` boundary tests under UBSan/ASan.
4. **P2 — AVI decode/read errors become successful playback** (`mciavi.c:289,384,649`): propagate preparation errors synchronously; terminate a running operation with exactly one `MCI_NOTIFY_FAILURE`; retain completion errors for waiting callers; test a valid first frame followed by corrupt media.
5. **P2 — AVI audio plays beyond the requested `to` position** (`mciavi.c:270,651`): compute the exclusive audio endpoint from the requested range, cap batching there, trim decoded ADPCM output at the boundary; add the audio oracle to the partial-range tests.
6. **P2 — device sharing checked by alias, not by resource** (`mci.c:340`, `mcicd.c:336`): separate alias uniqueness from canonical resource ownership; file devices (waveaudio, sequencer) are exclusive per Microsoft; a shared per-slot CD instance is refcounted only when both opens permit sharing; test both opening orders and alias variants.
7. **P2 — an empty CD drive at open disables analog fallback for the instance** (`mcicd.c:191`, `src/kernel/drivers/media_cd.c:70`): refresh INFO when capabilities are unknown and the drive becomes ready, recompute the path selection before playback; test empty-open → insert → extraction failure.
8. **P2 — MS ADPCM validation accepts nonconforming predictor tables** (`sdk/win32/codecs/adpcm.c:43`, `tests/host/win32/codecs/fuzz.c:98`): require the standard seven-pair prefix in order, allow appended coefficients; the fuzzer generates valid MS headers independently of iteration parity and covers all predictors, malformed tables, clipping extremes, header-only blocks, large geometry and multistrip Cinepak boundaries.
9. **P2 — dialog harness link error** (`tests/host/win32/dialogs/test_dialogs.py:139`): the dialog adapter lacks `host_pixel_format` (provider in `tests/host/win32/user32/gdi_host.c:191`); factor the helper into shared harness support so the dialog class runs.

Verification: the win32 discovery (`python3 -B -m unittest discover -s tests/host/win32 -t .`) with the media, codec and dialog classes executing; LeakSanitizer reruns are the lead's. Report section "Amendment 2".

## Amendment 3 (lead, 2026-10-21): the one finding left open by the re-review of ee911112

Apply this amendment only. **Finding 6 (device sharing by resource, P2):** the ownership key compares `GetFullPathNameA` strings (`sdk/win32/audio/mci.c:399`), which is lexical; FAT accepts a long name and its 8.3 alias for the same entry (`src/kernel/fs/fat.c:408`), so two MCI aliases can open the same WAV/MIDI exclusively through the two spellings. Key the ownership on the file identity instead: open the file and use the volume serial plus file index (`GetFileInformationByHandle` → `dwVolumeSerialNumber`, `nFileIndexHigh/Low`, which our kernel32 derives from the FAT directory entry's first cluster or the file identity f2-03 already maintains); fall back to the normalised path only for devices without a file. Test: open through the long name and the 8.3 alias in both orders, both must be refused the second time; distinct files with similar names stay independent. The lead's win32 suite run outside the sandbox on ee911112 was green (277 tests): keep it green. Report section "Amendment 3".
