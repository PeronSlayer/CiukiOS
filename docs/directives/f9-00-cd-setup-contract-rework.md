Lead decisions (binding):
1. **Volume binding (finding 1):** the kernel exposes a bounded, read-only 512-byte block view of the El Torito boot image over the native optical device (streaming, no RAM copy) and binds that FAT32 volume as `C:` in Setup mode; the emulated image carries the Setup runtime (loader, kernel, `/Programs/setup`, libdeskui, fonts, settings defaults), the payload stays on the ISO tree mounted as `D:`; `blkpart.c`'s 2048-byte parent rejection is lifted only for this view.
2. **No writes before Copy (finding 2):** Setup mode is recognised before writable activation: no FAT write enable, no disk logging, no pagefile, no repair on any ATA volume; destination disks are discovered read-only; an integration assertion keeps every ATA disk's write count at zero through discovery, preview, cancel and refusal.
3. **Layouts (finding 3):** the Beta installs only the **whole-disk layout on the supported boot disk** (ATA disk 0, partition 1 at LBA 2048, canonical geometry), which is what the unchanged loader boots; the free-space and advanced modes are shown disabled with the reason and move to a post-Beta directive with a loader/binding contract. Whole-disk erases everything, including foreign partitions and the loader gap; the confirmation screen states it.
4. **El Torito contract (findings 4, 5):** the boot image is canonical FAT32 (cluster count ≥ 65,525) with the smallest geometry the loader accepts (determine whether the loader pins sectors-per-cluster; if 1 sector per cluster is accepted, the image is ≈34 MB, otherwise budget the ≈270 MB and state it), a single partition in entry 1 with coherent CHS/LBA fields, catalogue checksums, media type, load count and image bounds specified; translation `image_start + floor(sector/4)` with the 512-byte slice; tests exercise EDD and CHS reads across 4-sector boundaries; the completed ISO is checked against 650 MB.
5. **Raw-disk ownership (finding 6):** an exclusive destination-disk lease acquired by Setup through the kernel (quiesces mounts, handles, writeback and pagefile users of that disk; refuses busy disks; invalidates partition/cache state before publication); authority bound to the Setup process identity granted by the supervisor at spawn (not to a path), checked on every mutating operation including ioctls and inherited descriptors, revoked at process death; the dry-run plan carries disk identity, capacity, table fingerprint and ranges, revalidated immediately before execution.
6. **Durability (finding 7):** persistent phases with an explicit incomplete-install state: partition+format → payload copy with flush and verification by reads that bypass the cache → configuration → loader install and `BOOT.CFG` **last** as the publication step; power loss before publication leaves a non-bootable, clearly marked disk and a clean reinstall from CD is the documented recovery; a native FAT consistency check (the kernel's fsck path or a bounded native checker) runs before publication; crash-cut tests drop unflushed writes at each phase.
7. **FDISK/FORMAT differences (finding 8):** documented deliberate policies: LBA-2048 alignment, fixed 4 KiB clusters, 160 reserved sectors with the blackbox layout of `build_image.py` (fix the stale 32-sector text in `boot-memory.md`), quick format with bad-sector handling by refusal (no surface scan), no resizing of occupied filesystems, 28-bit LBA limit per `partition.c`.
8. **Preflight and errors (finding 9):** a final transaction summary inside the Disk/Components flow (disk identity, erased partitions, required space including FAT overhead and pagefile reserve, source availability); CD read errors get bounded Retry/Cancel, reinserted media must match the release manifest, never Skip for required files, a failed source read leaves the install incomplete.
9. **Memory (finding 10):** pre-format Setup is RAM-only with bounded streaming buffers; a measured 128 MiB budget (kernel, cache, UI, verification) is an acceptance item; no optional personality, soundfont or game is launched during installation.
10. **Unattended (finding 11):** versioned `SETUP.INF` schema with strict validation, explicit `EraseDisk=yes` consent, stable disk selector (`Disk=ata0` or model+serial), `auto` refuses ambiguity; CD before USB precedence; missing answers stop with a status; the installed `BOOT.CFG` omits `setup=1`; the restart path ejects or waits for media removal and the test covers reboot with the CD inserted; offline installation allowed, network failures never block completion.
11. **Menu and CPU refusal (finding 12):** the loader stays unchanged: a CD boot goes straight to Setup (no new ten-second menu; the existing loader keys keep their meaning), the "boot from the first hard disk" entry is dropped from the Beta; an unsupported CPU or too little RAM is refused by the loader/kernel pre-graphics path with a text and serial message (screen 12 of the mockup becomes the graphical form only when the kernel runs); first boot persists a "test in progress" marker before activating the accelerator; finishing steps are idempotent with a durable completion marker; RTC and settings writes belong to the Copy phase's configuration step.
12. **Shareware and sources (findings 13, 14):** the component eligibility table is per component and fails closed: Wolfenstein 3D stays bundled by the owner's decision (dev diary 2026-10-21-05) with "permission not on file" recorded in the eligibility table; Quake's conditions documented; DOOM's exclusions kept; every copyleft binary shipped on the ISO ships its complete corresponding source on the ISO (GPLv2 §3(a)), including the unified DOS kernel fork, modifications, interface files and build scripts, independent of the optional "install sources" checkbox; notices preserved.
13. **Acceptance (finding 15):** the review's list becomes the f9-06 acceptance: CD-only boot to Setup with a blank destination; install, detach, cold boot, First boot complete; 128 MiB, multiple and occupied disks; zero pre-Copy writes; interruption, source-error, disk-full, flush-failure cases; keyboard-only and unattended; T23 optical install evidence with an explicit qualification limit for other BIOSes; immutable payload subset compared against the canonical manifest with rules for generated files.
14. **Sequencing:** f9-01 and f9-02 start only after this rework; f9-03/f9-04 share one transaction/progress/error interface defined in the plan.
