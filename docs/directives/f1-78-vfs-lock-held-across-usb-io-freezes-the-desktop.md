# f1-78 — the desktop freezes for the whole AutoPlay scan of a USB stick: the VFS namespace lock is held across device I/O, and the stick is read one sector per command

- **Phase:** F1 (storage). **Model:** gpt-6.1-sol / xhigh. **Worktree:** `wt/f1-78` from main `85299550`.
- **Authority:** `src/kernel/fs/vfs.h`, `vfs.c`, `mount.c`, `cache.c`, `fat.c`, `fs_ro.c`, `fs_port.h` (lock), `src/kernel/usb/usb_storage.c` (read sizing only), host tests `tests/host/fs/` (`fake.c`, `test_cache.c`, `test_storage.c`, `test_storage_namespace.c`, `test_throughput.c`, `test_powercuts.c`) and `tests/host/usb/` (`storage_test.c`, `f1_74_test.c`, `uhci_model.h`).

## Evidence (T23, image d598bf4c, disk logs `legacy/local/physical/d598bf4c/`, read-only)

- BOOT1.LOG 1765–1955 (menu L, DOOM running, stick inserted at tick ≈175 s) and BOOT2.LOG 371–417 (menu H, stick present at power-on): right after `[usb-storage] volume drive=E part=1 fat=32 mode=ro … clusters=1953289 spc=16` the desktop stall observer reports every 500 ms
  `[desktop] stall stage=shell worker=idle/idle no_frame_ms=715…8715 input_pending=0 work_pending=0 wait=folder-service wallpaper_wait=mailbox-wait autoplay_wait=media-scan`
  up to `no_frame_ms=8715` (BOOT1) and `8884` (BOOT2). The owner sees a frozen desktop after the removable-media popup.
- The stall ends exactly when the stick's controller worker returns: `[usb] worker controller=usb-1817 tick=186126 scans=1 elapsed_ms=8704 scans_per_second=0.114` (one port scan in 8.7 s: the worker executed the stick's transfers for the whole time). HID controllers (`usb-1813`, `usb-1821`) kept 4 scans/s.
- Per-command cost on this stick (Lexar 05dc:a81d, UHCI full speed): `stage=inquiry … elapsed_ms=586`, `volume … mount_ms=252` for `bind … reads=9 sectors=9 max_sectors=1` → about 28 ms per single-sector READ(10); `cadence … packets=121 poll_frames=704 retire_frames=244`. f1-74 measured 128-sector reads at about 310 KB/s on the same stick (6 MB in 19.9 s); single-sector reads deliver about 18 KB/s.
- Code: `vfs.h:26` declares one `fs_lock lock; /* namespace -> cache -> device */` for all 26 drives; every entry point in `mount.c` (e.g. 388, 409, 448, 459, 484) takes it; `cache.c` calls `d->read()` at 174, 247 and 280 and `write_block()` at 166 while holding `c->lock` under that namespace lock. `fs_port.h:65` `fs_lock_take` is a wake-all lock without ordering: the thread that just dropped it and re-takes immediately wins over the woken waiter.
- Consequence: the desktop frame thread's one-second poll of `C:\Documents\Desktop` (`apps/desktop/folder.c:140-153`, one syscall per readdir/stat) waits behind every stick sector the AutoPlay worker thread reads from E:, and is starved until the scan ends. Any other process reading the stick (Files browsing E:) freezes the desktop the same way. f2-78 moved AutoPlay off the frame thread; this is the kernel half of the same defect.

## Required

1. **No device I/O under the VFS namespace lock.** Split the single lock: a short namespace lock for node/description/table bookkeeping and drive attach/detach, and one lock per drive letter for FAT metadata, cluster chains and directory/file I/O of that volume. The block cache must not hold `c->lock` across `d->read`/`write_block`: reserve the slot in a *filling* state, drop the lock, perform the I/O, re-take, publish and wake; a concurrent request for the same block waits for the filler (`kwait`); a failed fill releases the slot with the error; `media_generation`, quarantine and `blkdev_range` checks stay exactly as strict. Document the lock order (namespace → volume → cache → device) in `vfs.h` and prove the absence of inversions in the host tests. The DOS VM disk gate and `storage_remove_removable` (surprise removal) must keep their guarantees.
2. **Fair lock.** `fs_lock_take` in the kernel variant of `fs_port.h` becomes FIFO (ticket or queue) so that a waiter is never starved by a thread that drops and immediately re-takes; the bounded 1000 ms safety wait and the `kpreempt_hold` semantics remain.
3. **Slow-device metadata reads.** A cache miss on a FAT or directory sector reads a run (the rest of the cluster, or up to `BLKDEV_READ_SECTORS`, bounded by the partition) with one command through the existing `cache_read_run` path and fills the cache, instead of one sector per command. Measure on the host USB storage model: listing a root directory with 64 entries plus 64 `stat` calls must issue at least 8× fewer BOT commands than today. Do not exceed the 128-sector reads f1-74 qualified; do not change the CSW handling.
4. **Host coverage.** (a) Thread A lists a directory on a slow fake device (`fake.c` gains a per-read delay of 25 ms) while thread B lists a directory on a fast device: every call of B completes in under 50 ms during A's scan (pthread build via `fs_port.h`). (b) Two readers of the same missing block: one fill, both see the data; a failing fill propagates the error and frees the slot. (c) Lock-order assertions in the pthread build. (d) `tests/host/fs/test_powercuts.c`, `test_write_in_place.c`, `test_log_recovery.c`, `test_storage_namespace.c`, `test_throughput.c`, `tests/host/usb/run.sh`, `tests/host/usb/storage_run.sh`, `ASAN_OPTIONS=detect_leaks=0 bash scripts/test/host_kernel_tests.sh`, `python3 scripts/build_kernel.py` all pass.
5. **Diagnostics.** `[storage] vfs_wait drive=%c ms=%u holder=%c reason=%s` (verbose class) when a namespace or volume wait exceeds 100 ms, so the next T23 log attributes any residual stall.
6. Report in `build/codex/f1-78-report.md`: design, lock order, command counts before/after on the host model, test outputs, what remains for QEMU/T23 (the lead runs `f1-usb`/media suites and the T23 trial).
