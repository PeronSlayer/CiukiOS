## Lead amendment 2 (2026-10-26 10:35): second review, and admission by sampling precision instead of colour match

Your review-round-1 fixes are committed as 154581a90. A second Codex review (high) found two P2s.

1. **Guard timeout masks corruption (fix as reviewed).** `savage3d.c:371` checks the chunk deadline before the value just read, so a corrupted guard byte (byte 508, 9 us/read) returns -ETIMEDOUT instead of -EIO; restoration succeeds, `lost=0`, no quarantine, and the timeout exemption at `render3d.c:452` keeps an engine that showed guard corruption. Check and record every mismatch before any deadline return; corruption always wins over timeout. Add the combined corruption+timeout regression.

2. **Colour tolerance is the wrong oracle for texture sampling (lead decision).** The second counterexample (triangle (0,0),(16,0),(0,16), white vertices, constant qw=1048576, both stages MODULATE/LINEAR/REPEAT, stage planes (1385+2x,1190) and (3522+2x,3570), 64x64 black texture with white texels at (1,0),(1,1),(3,3): GL/scalar ffc8c8c8, packet model ffcbcbcb at (0,0)) is caused by the 8-bit filter fractions of the software GL (`sdk/libgl/software/renderer.c:213`) against a different hardware fraction precision. With high-contrast textures any difference in sample position or filter-weight precision gives arbitrary colour differences, so "<=2 channel levels against software" can only ever admit draws whose sampling is bit-identical, and it already excluded all perspective (varying-W) geometry: with the current rule the whole Quake III world falls back to software and the Savage accelerates almost nothing. OpenGL 1.1 (section 3.8) leaves the precision of texture-coordinate interpolation and filter weights to the implementation, and the F7 contract (section 8) asks for **predeclared tolerances for coverage/interpolation**. Replace the colour-match admission with a sampling-precision model:
   - Model the Savage arithmetic in the fake engine as exactly as the primary sources allow (Mesa 7.7/7.11 savage driver vertex formats and texture setup, X.Org savage 2.3.9, Linux savage DRM, S3 RE046-B; local copies in build/downloads/f7-sources): perspective-correct interpolation of s/w, t/w and 1/w (or whatever the chip interpolates), texel-address precision and filter-fraction bits. Where a precision is not documented, make it a parameter of the model and of the probe.
   - Declare the tolerance in sample space: per pixel the hardware sample position may differ from the exact one by at most delta texels and the filter weights are quantized to N bits (choose delta and N from the sources, justify them, record them in docs/design/savage-fullsize-admission.md and the contract tolerance table). The differential oracle accepts a hardware colour when it lies within the envelope of reference colours over that neighbourhood (plus one level of rounding); coverage and depth (+-1 D16) stay exact as now. Missing pixels, cracks, wrong occlusion and wrong texture layout stay failures.
   - Extend the boot qualification (full-size step) to measure the real precision on the chip: a perspective ramp/gradient texture scene read back and checked against the declared delta/N; if the silicon exceeds them, perspective admission is refused (minimum and affine admission remain). Keep the 20 ms window, chunked readback and every existing guard/restore rule.
   - Admit varying-W triangles inside the proven numeric ranges (W ratio, coordinate magnitude with REPEAT, texture sizes, both stages), keeping refusal plus clean software fallback outside them.
   - Measure on the H1 Quake III replay (`--hardware-quake3`, demo frames): report per frame the draws and fragments executed on the Savage model versus software, the refused states with counts, and the number of hardware/software switches per frame. Target: at least 95 % of world and entity draws admitted at 640x480 and 1024x768. If per-frame alternation remains for the qualified set, report its cost and follow contract 7.2 (whole frame/context in software for unsupported state) unless the measured cost says otherwise; say which you chose.
   - Keep the existing differential cases and add: the two review counterexamples (now judged by the new oracle), perspective checkerboards and ramps with W ratios up to the admitted bound, both stages with independent planes, and the Quake III lightmap/base-texture combination.

Update the T23 procedure and the report (section "Review round 2"). Leave changes uncommitted.

## Lead amendment 3 (2026-10-26 11:10): make Quake III's real state set admissible, and measure the real game

Amendment 2 is committed as d056f47c2. Its own measurement shows the problem: on the complete H1 frame the Savage executes **0 %** because 400 sampled-alpha triangles per frame are refused and the context falls back as a whole (contract 7.2, which stays). `encode.h:49` refuses any varying-sampling draw with alpha test or blend, `encode.h:88` refuses mip with alpha test, and varying-W admission stops at 64x64 textures and |UV|<=4. Quake III's real surfaces use 128x128-256x256 base textures and 128x128 lightmaps, blended shader stages (sky, effects, lights, water, HUD/console), alpha-tested stages (grates, foliage) and tcMod scroll/scale. With the current predicate the game would always run in software. Fix that:

1. **Blending with sampled colour/alpha.** Admit textured draws with every blend factor pair the Savage supports and Quake III uses (at least ONE/ONE, SRC_ALPHA/ONE_MINUS_SRC_ALPHA, ONE/ONE_MINUS_SRC_ALPHA, DST_COLOR/ZERO, ZERO/SRC_COLOR, ONE/ZERO); the oracle propagates the source sample envelope through the blend equation against the exact destination (then one level of rounding).
2. **Alpha test with sampled alpha.** A pixel whose reference alpha envelope straddles the alpha reference may pass or fail (both acceptable, with the matching depth/colour consequences for that pixel only); pixels whose envelope is entirely on one side must match exactly (missing coverage there is still a failure). Include mip + alpha test.
3. **Ranges.** Extend varying-W admission to texture sizes up to 256x256 (and the Savage limits beyond if the precision model allows), lightmaps up to 128x128, and the UV magnitudes Quake III produces with REPEAT (tcMod scroll/scale), justified by the precision model (texel-address integer + fraction bits) and the boot precision phases; add phases if a larger size needs its own silicon check.
4. **Real-game census.** Add an opt-in opengl32 census (off by default, cost-free when off; enabled by a registry value under the existing opengl32/Win32 settings or an environment variable of the Win32 process, whichever the repository already supports for opengl32 options) that every N frames writes to the Win32 debug/boot log a compact histogram: state classes (texture size, filter, wrap, stages/env modes, blend pair, alpha test, depth func/mask, fog, polygon offset, W range, UV range) with draw and fragment counts, and the admission verdict against the reference qualified Savage capability (admit / refusal reason), plus whether the frame would have stayed on hardware under the whole-context rule. The lead will run the Quake III demo timedemo in QEMU (software GL) with it and send the numbers back. Document how to enable it.
5. **Remeasure** H1 (complete frames, 640x480 and 1024x768): target GPU execution of the complete frames, not only the prefix. Report refusals by reason. If some Quake III state cannot be admitted within the tolerance, say exactly which and why.
6. Tests: blend and alpha-test differential cases with perspective checkers/ramps and both stages, straddling-threshold cases, 128x128/256x256 textures with large REPEAT coordinates, census output format and its off-by-default cost.

Update the report (section "Review round 3"), the admission document and the contract tolerance table. Leave changes uncommitted.
