# f0-41 — a DOS VM's creation stalls the kernel for 110 ms (eager pool zeroing without preemption points); the audio lead then grows to 28 periods for the whole session

- **Phase:** F0/F3 (kernel core, DOS VMs). **Model:** gpt-6.1-sol / xhigh. **Worktree:** `wt/f0-41` from main (after `0aad7c2a`).
- **Authority:** `src/kernel/vm/dosvm_xms.c`, `src/kernel/vm/dosvm.c` (creation, `transfer`, `dosvm_text` loops), `src/kernel/vm/dosvm_disk.c`, `src/kernel/fs/mount.c:472` region (write enable scan), `src/kernel/core/task.c`/`sched` only for a bounded helper if one is missing, `src/kernel/audio/audio_dev.c` only for item 3, `tests/host/` (dosvm, kernel latency, audio), `docs/validation/f0-40-reliability-audit.md` (new section F0-41).
- **Not yours:** DPMI dispatch (f3-45 runs in parallel in `wt/f3-45`), the Files application (f2-84), display drivers.

## Evidence (T23, image c2d2a237, `legacy/local/physical/c2d2a237/serial.log`, read-only)

- At every DOS VM creation the creating task stretches for 110 ms without yielding: `[audio] transport idle-stop … gap_us=111878 … task=dosbox stretch_ms=110` (VM 1 at 95 s), `[kernel] stretch_max_ms=110 task=dosbox#31 eip=c017fac2 resched_lat_max_ms=110 resched_task=dosbox irqoff_max_us=2129`, and again at the Quake VM: `[launch-stage] name=dosbox pid=7 stage=vm-create window=Quake` followed by `[audio] transport late-grow published=1925 retired=1917 … gap_us=113127 lead_periods=28 … task=dosbox stretch_ms=111`, `underrun`, `recover-stop`, `recover-start published=28`.
- Consequence: the f4-31 adaptive lead grows to 28 periods (149 ms of output latency) and stays there for the session (`lead_periods=28` at every later `source-stop`), so every game after the first VM start plays its sound effects 149 ms late. The 113 ms "refill gap" measured on 9af46936 was this same stall.
- The stall site: `dosvm_memory_init` (`dosvm_xms.c:124–135`) allocates, zeroes and maps the whole pool quota (`v->memory.quota`, up to `VM_POOL_CAP`) page by page with no `kpreempt_point`; `dosvm_create` has points for its structure and low-memory pages (`dosvm.c:1140`, `1165`) but not here. Codex's F4-32 report also lists `dosvm.c:388` (`transfer`/VGA-model loops without internal preemption points) and `mount.c:472` (write enable can reach a full-volume scan).
- The IRQ 11 handler still runs 2.1 ms with interrupts off (`irqoff_section=irq11 site=c0100eb1 irqoff_max_us=2129 violations=171`; `[irq] budget exceeded irq=11 owner=ac97 us=2104`): known since f0-39 (SMI attribution), not this directive's subject unless the section is a code loop you can bound.

## Required

1. **Bound every kernel section on the VM creation path to ≤ 2 ms without a preemption point.** `dosvm_memory_init`: `kpreempt_point()` after every N pages (choose N from the measured per-page cost: allocate + zero + map ≈ µs on a 1.1 GHz Pentium III; write the arithmetic), or zero lazily on first touch if the pool pages are only mapped user-writable and the first access can be trapped cheaply; keep admission semantics (the pool is reserved at admission). Audit `dosvm_create`, `dosvm_boot`, disk image reads at boot (`dosvm_disk.c`), `transfer` for ≥ 1 page copies, `dosvm_text`, and `mount.c:472`: every loop that can run longer than 2 ms gets a bounded point, outside IRQ-off sections and with no lock held across the point. Record each bounded site in the audit section with its worst-case before/after on the host model.
2. **Host evidence.** Extend `tests/host/test_kernel_latency.py` or the DOS VM harness with a creation of a maximum-quota VM under a timing model that counts instructions/pages: assert the longest non-preemptible span ≤ 2 ms-equivalent and the total creation time unchanged within 10 %. The existing `stretch_max_ms` instrumentation must see ≤ 2 ms for the dosbox task on the host replay.
3. **Audio lead growth after a one-off stall.** With the stall gone the lead must not grow at VM creation; add a host case: VM attach + creation replay with the new points → `late-grow` never fires, `lead_periods` stays 8. Do not change the f4-31/f4-32 lead policy itself; if a residual stall still grows the lead, report its source instead of hiding it.
4. **Verification.** `ASAN_OPTIONS=detect_leaks=0 bash scripts/test/host_kernel_tests.sh` complete and green, `bash tests/host/audio/run.sh`, `python3 scripts/build_kernel.py`. Report `build/codex/f0-41-report.md` with the per-site table (site, loop bound, points added, worst span before/after) and remaining.
