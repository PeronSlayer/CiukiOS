## Owner decisions (2026-10-26, binding)
- CiukiOS moves from the Windows 98 profile-only logon (G32, `docs/design/users-and-logon.md`) to **real users with administrator roles enforced by the kernel** (Windows 2000/XP class). This supersedes, for users and security only, the owner's 2026-10-22 "Windows 9x model everywhere" decision.
- **CiukiUser**: the default standard administrator account (member of Administrators). On ready-made images that do not go through Setup (QEMU/VirtualBox/VMware packages, raw disk image) the system logs on directly as CiukiUser, which has no password.
- **CiukiAdministrator**: the super administrator (built-in Administrator, NT RID 500 equivalent). Disabled and hidden by default; its password is chosen in Setup; it appears at logon in Safe Mode or when an administrator enables it.
- **Guest**: exists but is disabled by default. While Guest is disabled there is no way in without a valid user name and password: the G32 rule "Cancel at logon = default profile" is removed.
- **Setup** must force the creation of a custom user (it becomes the first administrator; Setup installs do not create CiukiUser) and asks for the CiukiAdministrator password.

## Lead decisions shared by both contract parts (keep them identical; if you find one wrong, say so in your report instead of diverging)
- Identities: 32-bit user ids. 0 = SYSTEM (kernel, boot services, the logon/account service); 500 = CiukiAdministrator; 501 = Guest; 1000 and up = ordinary accounts (CiukiUser or the Setup user is 1000). Ids are never reused.
- Groups (NT well-known RIDs as numbers): 544 Administrators, 545 Users, 546 Guests. Account types shown to the user: Administrator (544+545) and Standard/Limited user (545); Guest (546).
- Each process carries an immutable credential record {uid, group set, session id, flags}; children inherit it; only SYSTEM (the logon service) can create a process with a different credential. No setuid binaries. Administrators run with full administrator rights (Windows XP model, no UAC split token). A "Run as administrator" credential prompt may come later and is out of scope unless the contract finds it needed for installers.
- FAT32 has no ACLs (Windows XP on FAT32 has no file security at all); CiukiOS enforces a **kernel path policy** on its own volumes: rules by path prefix plus owner metadata for profile trees, stored in a SYSTEM-only place. Windows XP default NTFS permissions are the model for what Users/Administrators/Guests may do in the root, Windows/System, Program Files, Documents and Settings (Profiles) and settings directories.
- Account database: SYSTEM-only (path policy), salted PBKDF2-HMAC-SHA-256 verifiers as in G32 (re-tune iterations for a Pentium III if needed and say why), recoverable locking (no stale lock can block management).
- Physical access is out of the threat model (a FAT32 disk is readable from another OS); no disk encryption, no network authentication in this step.
- Existing per-binary "authority" mechanisms (`docs/design/execution-abi.md`, CIUKI_*_AUTHORITY, `--authority-fd`) are inputs: map each to the new model (admin-only, SYSTEM-only, or per-user) rather than keeping two parallel systems.

## Scope
Write the kernel half of the contract: (1) an inventory of EVERY syscall/call/action in src/kernel/include/ciuki/abi.h and docs/design/execution-abi.md with its current authority and the proposed class (anyone / own-session / administrator / SYSTEM), with file:line evidence; (2) the credential record in the process model (src/kernel/proc and friends): creation, inheritance on spawn/exec, the SYSTEM-only call that sets a credential, query calls (getuid/getgroups-like for the POSIX libc, token query for Win32), session ids and how logoff ends a session; (3) the VFS path policy on FAT32/FAT16/FAT12 and CD/USB media: rule table, owner metadata for profile trees, evaluation on open/create/rename/delete/mkdir/rmdir/exec/mmap/truncate/attribute change, case-insensitivity, 8.3 aliases and long names, `..`, rename/move across policy boundaries, open handles across logoff, removable media policy (Windows XP: users can use removable media; say what we do), the DOS file API in the VMM and DOS VMs (each VM runs with its owner credential; INT 13h/raw sector access only on virtual disks), and the Win32 file paths through w32srv; (4) device, raw disk, partition/format/ScanDisk/defrag, driver loading and hardware profile, power (shutdown/restart allowed to any interactive user as in Windows XP defaults? research and decide), time and time zone, network configuration, display mode, process control across users (Task Manager kill), recovery authority; (5) ABI additions with the oracle rules (one field per line, abi_layout rows) described but not implemented; (6) performance cost on the hot paths (path policy lookups must be bounded and cheap on a Pentium III) and failure modes (no panic paths); (7) test plan (host tests per enforcement point, adversarial cases) and the implementation directive split for the kernel side, each with acceptance criteria.
