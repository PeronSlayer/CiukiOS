# f0-42 — Windows 98/ME-class management of disk, memory, cache and real-time: research, gap audit and design contract

- **Phase:** F0 (foundations). **Model:** gpt-6.1-sol / xhigh. **Worktree:** `wt/f0-42` from main (after `3fbffcde`).
- **Deliverable:** `docs/design/win98-class-resource-management.md` (the contract) and `docs/validation/f0-42-resource-management-audit.md` (the audit), plus the report `build/codex/f0-42-report.md`. **No kernel code in this directive.** Implementation directives follow per subsystem after the lead's cross-review.

## Owner decision (2026-10-19, dev diary 2026-10-19-03)

CiukiOS must manage disk, memory, cache and real-time the way Windows 98/ME does, completely: "non far fare cose base, dobbiamo andare pari pari, così che abbiamo una gestione di disco, memoria, cache e roba in tempo reale completa e non solo abbozzata". The hardware class is the one of `docs/design/hardware-baseline.md` (Pentium III laptops and 1998–2004 desktops, 128–512 MiB).

## Required

1. **Primary sources first.** Read and cite: the Windows 98 Resource Kit (performance tuning chapters: VCACHE, swap file, "Optimizing Windows 98"), the Windows 98 DDK documentation of VMM services (memory manager, paging, working sets, thread scheduling and priority boosts, timers, `VMM` services list), IOS (I/O supervisor: IOP/IOR request packets, layered drivers, volume trackers, `ESDI_506.PDR`, bus-master DMA, scatter-gather), VCACHE (unified block cache: dynamic size with `MinFileCache`/`MaxFileCache`, lazy writing, read-ahead `ReadAheadThreshold`, cache coherency with memory-mapped files), IFSMGR and VFAT (long names, locking, lazy-write ordering), VREDIR/VSERVER only to note what is out of scope; plus the technical literature on Windows 95/98 internals (Schulman "Unauthorized Windows 95", Pietrek "Windows 95 System Programming Secrets", Oney "Systems Programming for Windows 95" for VxD/IOS/VMM mechanics). Microsoft KB articles on VCACHE and conservative swap file usage count as primary. Record each source with the facts taken from it.
2. **Model description.** For each subsystem write the Windows 98/ME behaviour precisely (numbers where they exist): cache sizing policy and its triggers, lazy-write delay and ordering, read-ahead policy, write-behind for removable media, eviction, memory manager page replacement and working-set trimming, swap-file growth policy, demand-zero and copy-on-write, DMA buffering and 64 KiB boundaries, I/O request queuing and priorities, thread priority classes and the dynamic boosts (foreground, I/O completion, starvation), timer resolution and the scheduler quantum, real-time constraints on interrupt handling (VxD interrupt latency, `VPICD`, deferred procedure handling), and the DOS box integration of these (V86 memory, DOS disk I/O through IOS).
3. **Gap audit against this kernel.** A table per subsystem: Windows 98 behaviour, current CiukiOS behaviour (file and function), gap, risk shown by the physical trials (cite the dev diary entries 2026-10-17-02 to 2026-10-19-02 and the records that proved each defect), priority. The storage rows must include the f1-82 findings (synchronous dirty eviction under the volume lock, 5 s barrier, 8 MiB fixed cache), the memory rows the current `pmm`/`vmm`/`as_` design (no paging to disk, fixed allocations, `DOSVM_RESIDENT_CAP`), the real-time rows the measured facts (stretches, `irqoff_section=irq11` 2.1 ms, preemption points added by f0-41, P_DEVICE audio refill, 1 kHz tick).
4. **Contract.** `docs/design/win98-class-resource-management.md`: the target design for CiukiOS per subsystem, written as acceptance criteria that a host test or a physical record can check (for example: "a 10 MiB copy at device speed never delays an unrelated 16 KiB read by more than 20 ms"; "dirty data older than 1 s or above N % of the cache is being written"; "foreground window thread gets a +2 boost for 20 ms after input"; "no section longer than 2 ms with preemption disabled outside IRQ-off paths; no IRQ-off section longer than 100 µs outside firmware"), the data structures and interfaces to add or change, the order of implementation with one directive id per step (f1-8x storage, f0-4x memory, f0-4x scheduler/real-time, f3-4x DOS integration), and what is explicitly not adopted from Windows 98 with the reason (for example cooperative 16-bit Win16 scheduling, VxD loading).
5. **Scope limits.** No code. No change to decisions already taken by the owner (one image per machine class, F-steps order). Where Windows 98 behaviour contradicts a measured CiukiOS requirement (for example the audio refill deadline), state the conflict and propose the resolution for the lead.
6. **Report** with the list of sources, the gap table summary (counts by priority) and the proposed directive sequence with sizes.
