Required:
1. **Trigger and resumption.** On a normal boot, when `C:\SYSTEM\SETUP.STATE` has `phase=installed` and `firstboot=pending`, the desktop runs the wizard (screen 11 of the mockup) before the ordinary session; the wizard reads the `step=<name> result=<ok|skipped|failed>` lines and resumes at the first step without a result. Each step is idempotent (re-running a completed step is harmless) and appends its line with `fsync` immediately after finishing. Completion writes `firstboot=done` and the desktop continues; the file is never deleted. Without the file or with `firstboot=done`, nothing of this directive runs (the canonical image boots exactly as today: the `normal-boot` milestones are unchanged).
2. **Steps**, in order, each bounded: `accel` (no activation here: the kernel already attempted acceleration under its marker during this boot; the step reads the result — the `[accel]` activation record/the display page's state — and shows "Hardware acceleration is on" or "Software rendering is in use; you can retry from Control Panel → Display" with the retry button that the Control Panel provides; a marker left set by a hang on the previous boot is exactly this second case), `sound` (play the startup sound through the audio service with a 10 s bound; report present/absent), `network` (configured mode from the settings; DHCP wait ≤ 10 s; report address or "no network"; never blocks), `games` (register the bundled games with f2-87's registration if not registered; idempotent by shortcut identity), `entropy` (report `[entropy]` readiness; no wait beyond 5 s; HTTPS readiness text as `docs/desktop.md` describes), `clock` (show the time and date resulting from the RTC and the configured convention, "Change" opens the clock page), `summary` (what was installed, where `SETUP.LOG` and `HARDWARE.TXT` are, Finish). Every step's result goes to `SETUP.STATE` and the kernel log (`[firstboot] step=<name> result=<r> ms=<n>`).
3. **Rescue tools** on the Setup CD's Rescue page (f9-03 stubs): list disks and volumes (from `libdisk` enumeration, read-only), export `SETUP.LOG`, `HARDWARE.TXT`, `SETUP.STATE` and the disk log of an installed disk 0 to the first USB FAT volume (`\CIUKIOS-RESCUE-<date>\`), show the hardware report; no write to any ATA disk; every action logs `[rescue] action=<a> result=<r>`.
4. **Documentation:** `docs/desktop.md` "First boot" section (what the steps do, what the accelerator message means, where the records are) and the plan's §9 kept consistent (propose edits in the report).

Host tests (`tests/host/desktop/firstboot_test.c` with the desktop test harness; a FAT model volume with `SETUP.STATE` fixtures):
- Trigger matrix: no file / `firstboot=done` / `pending` with no step lines / `pending` with three completed steps → the wizard runs or not and resumes at the right step; a crash fixture (file with a step started but no result) resumes at that step.
- Idempotence: running every step twice produces one result line per step per run and no duplicate game registrations; the game registration step with the catalogue fixtures.
- Bounds: fake sound/network services that never answer → the step completes as `failed`/`skipped` within the bound and the wizard continues; completion still writes `firstboot=done`.
- Accelerator outcome rendering for the three states (on, software after a failed attempt, software because the marker was set by a previous hang) from fixture records; the retry button invokes the Control Panel action (fake counter).
- Rescue export: the export tree on the USB model with the expected files; refusal when no USB volume; the ATA write counter of the disk model stays zero.
- Render goldens for screen 11's states.
