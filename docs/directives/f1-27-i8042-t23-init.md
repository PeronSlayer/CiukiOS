## Observed on the ThinkPad T23 (image `9218d595…`, commit `6da9b9c`, serial captures `a1b2c3d4…d6`, 2026-10-11)

In every boot of the F2 image on the T23 (five boots, two images) the
native input driver fails at initialisation:

```
[init] input result=failed error=-5 reason=native activation_seq=3 tick=146 safe_flag_before=0
```

and the `input` probe reports only
`case=setup backend=native error=-5` followed by `END status=FAIL
reason=setup`, after which the `f1:all` alias marks the remaining F1
probes not run. One earlier boot (image `b9c052cd…`) initialised the
keyboard successfully and the desktop received keys, so the failure is
not deterministic. On QEMU every input case passes. The driver's
`i8042_init` returns `-I8042_EIO` from several steps without saying
which: self-test reply ≠ `0x55`, interface test replies ≠ `0`, the
configuration byte read back with translation/interrupt bits still set,
or `IBF`/`OBF` still asserted in the status port after setup
(`i8042.c` lines 650–745). The T23 keyboard controller is the embedded
controller's 8042 emulation; the TrackPoint hangs on the AUX port. The
serial capture of the probe run is in `build/f1-27/serial.log` of the
worktree.

## What to do

1. **Diagnostics first.** Make every initialisation step observable:
   emit one bounded record per step in the `input` probe's setup
   (`case=setup step=<self_test|iface_kbd|iface_aux|config_read|config_write|flush|enable|reset_kbd|reset_aux>
   command=<hex> reply=<hex or none> status_before=<hex> status_after=<hex>
   elapsed_ms=<n> result=<n>`) and the same facts as `[i8042] step=…`
   klog lines at boot (bounded to the steps, no per-byte logging). The
   records MUST name the first failing step and the raw bytes seen.
2. **Research and fix what the evidence already allows.** Compare the
   driver's sequence with SeaBIOS `ps2port.c` (which works on this
   machine) and with the Linux `i8042` driver's known ThinkPad handling:
   controllers that leave translation enabled or report the configuration
   byte differently, self-test that disables the interfaces and needs a
   second configuration write, AUX interface tests that fail without an
   AUX device, status bits that stay set until the output buffer is
   drained, reply timing longer than the 200 ms deadline on a real EC.
   Where the sequence is wrong against the references, correct it; where
   the deadline is too tight for real hardware, change it within the
   contract (say so) rather than retrying blindly. The driver MUST still
   refuse to run when the controller never reaches the configured state,
   with the diagnostic naming the step.
3. **Host tests.** The i8042 host harness replays the controller
   behaviours above (translation left on, delayed `0x55`, AUX test
   failure, stuck `OBF`) and checks the step records and the resulting
   verdict; predicate tests with the probe's own formatting.
