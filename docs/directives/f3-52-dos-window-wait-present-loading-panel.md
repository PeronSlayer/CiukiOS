- **Written:** 2026-10-20 by the lead from the T23 trials of images `3d18f2db…` and `5b74e640…` (logs under `legacy/local/physical/`, read-only) and the QEMU comparison run of the same image

## Evidence

- T23, DOOM from Programs > Games: after the games-disk hash and the WAD read (`[launch-io] disk_bytes=23795712`, then about 5 MB more), `[cpu] top=dosbox#35:700k700s7` — the **DOS Box application** task at 50–70 % CPU, all of it kernel time, `stretch_max_ms=11 task=dosbox eip=kpreempt_point`, while the VM thread `dosvm#37` gets about 5 % (`dosvm#37:50k49s1`); `[cpu] task=dosbox#35 class=2 base=9 effective=10`, `task=dosvm#37 class=2 base=7 effective=7`; the CPU is saturated (`idle_pm=8..51`). The game never presents a frame; the owner sees the loading page and closes the window (`[dosvm] lifecycle stage=stop reason=1`). Quake: the same.
- QEMU (TCG, same image): `dosvm#32` at 58–64 %, `dosbox#30` at 5–11 %, DOOM reaches its title.
- `apps/dosbox/dosbox.c` (around lines 336–360): while the window is focused the application calls `ciuki_dosvm(CIUKI_DOSVM_PRESENT_BANDS)` and sleeps **2 ms** (10 ms unfocused): about 500 syscalls per second. `src/kernel/vm/dosvm_client.c:293`: every call pins the client surface (`ua_pin`/`ua_unpin` around the request, f0-44 pin accounting), wakes an idle VM (`dosvm_idle_wake`) and runs `dosvm_vga_present` (`dosvm_vga.c:840`; cheap when the model is unchanged, a full row conversion when it changed). On a Pentium III this per-call kernel work at 500 Hz, at a priority above the VM thread, is where the application's kernel time goes and why the VM thread starves; on a fast host it is invisible.
- The loading panel (`dosbox.c:355`, `loading.h:17`) repaints the whole 640×400 canvas and sends a full-window `DESK_DAMAGE` every **80 ms** (12.5 per second) to move a 48×10 pulse; the settings panel repaints every **20 ms** (`dosbox.c:261`) and the fullscreen-error notice every **10 ms** (`dosbox.c:301`), both static. Each full-window damage costs the desktop a software composite and, with the Savage quarantined on the T23, about 1 MB of LFB writes.

## Required

1. **Blocking frame wait in the kernel.** A new DOSVM operation (`CIUKI_DOSVM_WAIT_PRESENT` or a wait flag with a timeout field on `PRESENT_BANDS`; the ABI record is versioned, extend it the way earlier F3 directives did) that puts the calling thread to sleep until one of: new dirty rows/bands since the last present, a video mode or geometry change, a console line, a VM state change (stop, fault, fullscreen), or the timeout (bounded, ≤ 50 ms; the application passes the VGA frame period). Interruptible by signals and process exit; one waiter per binding; no busy loop. The wake comes from the VM worker where it already marks dirty granules (`video_harvest`/`vga.dirty`) and from the lifecycle paths; no wake of an idle VM from the present path unless a present is actually due (`video_due_us`).
2. **Pin cost.** The present path pins only what it writes (the damaged rows of the client surface) or keeps the surface pinned for the binding's lifetime under the f0-44 rules — choose with measured pin counts in the host VM harness and record the numbers; the unchanged-model path must perform no per-call pin walk.
3. **The VM thread runs while its window waits.** Establish from `src/kernel/core/task.c`/cpustat (f3-41) why `dosvm` has base 7 and the application base 9, and make the window's blocking wait hand its effective priority to the VM thread it waits on (inheritance across the binding, released when the wait ends), or raise the VM thread's base to the application's for the binding's lifetime; whichever the f0-42/f3-41 scheduler contract allows, with its bound stated. A focused window's input boost must never let the application outrun the VM it is displaying.
4. **Application.** `dosbox.c` uses the wait (frame-paced by the VM, no fixed 2 ms sleep); the loading panel paints its static content once, animates the pulse at **≤ 4 updates per second** with elapsed-time positioning and damages only the bar (or the union of the old and new pulse rectangles); the settings panel and the error notice repaint only on a state change. The existing `[launch]`/`[launch-stage]` records and the loading-page texts stay.
5. **Tests.** Host VM harness (`tests/host/vm` or wherever `dosvm` host tests live): the wait returns on each wake reason and on timeout, is interruptible, performs no pin walk on the unchanged path (pin counters), and the VM thread receives the inherited priority while a waiter sleeps (scheduler unit test in `tests/host/proc` with the fake clock); `tests/host/desktop/dosbox_loading_test.c`: repaint and damage counts per second for the loading, settings and error panels; `make CAP= apps` once; kernel compile with the production flags. No QEMU: the lead runs DOOM and Quake in QEMU and on the T23 with the f1-86 records.

## Amendment 1 (lead, 2026-10-21, from the Codex cross-review `build/lead-scratch/f3-52-review.md` in the main checkout: verdict "merge with these fixes")

1. **Permission-checked command transfers.** The WAIT/PRESENT record is read and written through bounded, permission-checking transfers (readable input, writable output, validated inside the range reservation), never through the supervisor-resolving `ua_read`/`ua_write` path; the record stays unpinned across the sleep; the documented `EFAULT` for a record protected while the waiter sleeps is real. Tests on the real uaddr model: read-only record, `PROT_NONE` record, protection changed during the sleep.
2. **Fractional frame cadence preserved.** The wait deadlines keep the fractional phase (quantize each absolute deadline once, as `video_due_us` does): sustained 70.09 Hz and 35 Hz through WAIT → PRESENT with delayed samples, tested.
3. **Integration tests that depend on the production notifications.** The VM wait tests must fail when a production wake source is missing (no 1 ms predicate polling in the fake; no explicit checkpoint/notify calls from the test); a combined scheduler replay with donation enabled, the focused VM, the desktop at priority 9 and device load, checking desktop latency and device budgets; app scenarios where the wait returns TIMEOUT and STATE without VIDEO.
